# 테스트 코드

> 읽는 때: 단위테스트를 쓰거나 고치거나 실행할 때. 색인은 `index.md`.

### 프레임워크·구조·fixture (2026-07-10, 병합 2 · 최근 11-10)
- Kotest BehaviorSpec(Service/Entity)·DescribeSpec(Controller/unit), MockK, Fixture Monkey, 테스트 설명은 한국어
- `context("메소드명 검증")` > `Given("전제")` > `When("조건")` > `Then("결과")` 엄격 준수. Aggregate Root 중심, 하나의 테스트는 하나의 시나리오, 성공/실패 모두
- 식별자 매칭 + 미발견 예외 로직(`find { it.key == input } ?: throw`)의 단위테스트는 fixture 의 매칭 키를 호출 입력과 동일하게 `set("key", 고정값)` — 랜덤 키는 항상 미발견 예외만 탄다. 여러 엔티티 공존 시 매칭 대상만 입력 키와 일치, 나머지는 다른 키(우연 통과 방지), 미발견 케이스는 어떤 fixture 키와도 안 겹치는 입력. 시그니처에 매칭 파라미터가 늘면 mock stub/verify 인자도 정합

### 단위테스트 작성 대상 (2026-05-06, 보강 7 · 최근 11-11)
- 자동 작성: 데이터 구조(VO/enum/일급 컬렉션/Group)의 변환·분기·예외·derived properties — 만든 자리에서 BDD 시나리오로, Fixture Monkey 생성 + 협력자만 mock. 명시 요청 시에만: Facade, Controller, Service — 비즈니스 로직이 있는 `{Domain}CommandService` 도 포함("단순 위임이 아니니까" 는 자동 작성 근거가 아니다)
- 상대 저장소에 API·서비스 메서드를 추가할 때도 서비스 테스트를 끼워 쓰지 않는다 — 승인 문구에 테스트가 없으면 작성 대상이 아니고, 생성자 변경으로 컴파일에 필요한 mock 주입 수정만 한다
- 전용 테스트 X: 분기·가공·예외 없이 1:1 로 옮기는 매핑(`toMessage`/`toResponse`), 읽기 모델의 단순 조회(filter + flatMap 의 `getXxx`), 엔티티 키 조립·스키마 속성 집합(`of`/`getPk`/TableSchema), `{System}Constants` 의 식별자 포맷 조립(구분자 결합 한 줄), enum 코드 목록과 문서 대조, 필드 존재만 보는 술어(`hasXxx`), 입력 누락 null 가드, 미지원 타입 예외 분기. 이벤트 등록·상태 전이·불가 상태 예외는 애그리게이트 테스트가, 조회는 호출하는 서비스·이벤트 테스트가, 포맷 조립은 서비스 시나리오의 단언값이 덮는다. TDD 의 red 대상은 분기·파생이 있는 로직뿐 — 매핑에 포맷·계산·조건이 생기면 그 분기만
- Service/Processor 라도 환경(prod/비prod)×테스트 마커 같은 운영 정책 분기는 비즈니스 로직 — 자동 작성은 않되 계획의 테스트 범위 옵션에 '분기 시나리오 N건' 으로 올려 확인받는다
- 반대로 제어 흐름만 바뀌는 변경(단계 격리·에러 집계 등)은 기존 ServiceTest 가 있어도 테스트 범위를 옵션으로 묻지 않는다 — 계획엔 '테스트 변경 없음(요청 시 시나리오 N건)' 1줄, 새 단계 stub 이 없어도 기존 단언이 통과하면 stub 보강도 않는다. 새 동작은 임시 테스트로 확인 후 지우고 '이 동작을 지키는 저장소 테스트 없음' 1줄
- **왜:** 단위테스트는 결정론적 로직(분기·파생) 보호에 적합 — 1:1 복사·구조 확인은 깨질 로직이 없고, 통합 wiring 은 mock 노출만 늘린다

## 하지 말아야 할 것

### 실패 테스트 — 실행 증거로 "테스트 vs 프로덕션" 판별, 수정은 테스트 계층 안에서 (2026-06-26, 보강 1 · 최근 11-06, 병합 1 · 최근 11-10)
- 판별 먼저: 실제 실행 + 스택트레이스 확보 → mock stub 이 실제 호출 시그니처와 안 맞음(테스트 문제) vs 현실적 입력에서 제약 위반(프로덕션 문제)을 구분해 근거와 함께 보고 — 추측 판별은 맞는 테스트를 고치거나 진짜 버그를 덮는다. 현실 입력에서 깨지는 테스트는 보통 프로덕션 버그 신호
- 테스트를 통과시키려는 프로덕션 타입/설계 변경·테스트 파일 삭제는 확인 없이 하지 않는다 — 발견과 제안만 보고
- 프로덕션이 진행 중 리팩터(WIP: 디버그 잔재, 절반 바뀐 시그니처)면 대량 수정 전에 불일치·방향부터 보고
- 예외: 현실적 입력에서 깨지는 실제 프로덕션 버그는 수정 — "컴파일용 타입 변경"과 구분. 단 사용자가 방금 직접 바꾼 값의 하류 결과(전송 금액이 0 이 됨 등)는 예외가 아니다 — 의도일 수 있으니 고치지 않고 "이 값이면 하류가 X 로 나간다" 한 줄 + 질문으로 남긴다
- **왜:** 의도는 "테스트를 맞는 상태로"이지 설계 변경이 아니다. WIP API 에 맞춘 수정은 곧 유실된다

### rapid iteration 중 매 변경마다 전체 테스트 재실행 금지 (2026-07-21)
- 작은 변경 연속 국면에선 코드 수정 + 테스트 동기화만, 실행은 사용자 요청/작업 마무리 체크포인트에서만. 미실행이면 "갱신만 함(미실행)" 1줄 명시
- **왜:** 매 tweak 마다 전체 재실행은 노이즈. 검증은 완료를 주장하기 직전에 하면 된다

## 더 신경써야 할 것

### 데이터 구조 우선 단위테스트 + TDD 사이클 (2026-05-06, 보강 1 · 최근 05-28)
- ①티켓 분석 ②계획 확인 ③데이터 구조 정의(VO/enum/Group/Message) ④데이터 구조 단위테스트(BDD red) ⑤사용 측(Facade/Controller) 구현 ⑥빌드 검증
- 테스트 단계는 TDD 사이클 엄격 적용: 시그니처 stub(`TODO()`) → 모든 분기+예외 테스트 → red 확인 → 본문 구현 → green 확인 → 전체 회귀. 한 번에 본문까지 작성하지 않는다
- 자동 작성 대상은 데이터 구조 위주 — Facade/Service 단위테스트는 명시 요청 시에만, 계획에 넣기 전 확인(이 파일의 "단위테스트 작성 대상" 이 단일 소스)
- **왜:** red 를 명시적으로 거쳐야 테스트가 계약 선언이 된다 — 아니면 회귀 테스트로 격하
