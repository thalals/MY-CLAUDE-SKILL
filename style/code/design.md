# 구조·추출·재사용

> 읽는 때: 메서드·클래스를 새로 만들거나 추출·리팩토링·삭제할 때. 색인은 `index.md`.

### 과잉 설계 금지 (YAGNI, 보강 6 · 최근 11-02)
- 지금 호출되지 않는 메서드/GSI/TTL 을 미리 만들지 않는다 — 구현 전 "지금 실제로 호출되는가?"
- 드문 케이스(같은 키가 여러 하위 아이템에 분산)용 분배 로직을 선제 구현하지 않는다 — 단건 탐색 + 불일치 예외로 드러내고 실제 발생 시 확장, 갱신 메서드는 "찾고, 검증하고, 갱신"
- 상위 단위가 단건이면 `Map<상위키, List>` 그룹핑 대신 단건 getter(둘 이상이면 식별자 포함 ServerException) + 목록 getter
- 엔티티 속성은 코드가 읽는 것만 — 형제 엔티티 필드(channel_type/created_at/ttl)를 관례로 복사하지 않는다. 반대로 코드가 읽는 식별자는 SK 와 같은 값이라도 파생 getter 가 아니라 저장 속성으로
- 호출 1회 절약용 게이트(다른 응답의 파생 신호가 있을 때만 권위 있는 조회를 부름)를 선제로 넣지 않는다 — 판정 근거가 두 소스로 갈리고 두 응답 사이 시차만큼 놓친다. 판정은 그 사실을 직접 주는 조회 하나로, 게이트는 호출 비용이 실측 문제일 때만
- 새로 넣는 배포 전 레코드 호환 fallback 도 같다 — 레코드 데이터 상태별로 그 경로를 실제로 타는지·타면 올바른 결과를 만드는지 표로 확인, 안 타거나 실패 양상만 바꾸면(조용한 불일치 → 예외) 넣지 않는다
- 요청 목록 ↔ 보유 목록 매칭의 가드는 '요청 키가 보유 목록에 없음 → 식별자 포함 예외' 하나 — 정상 요청이 가리킬 수 없는 라인(증정품) 제외 필터, 같은 키 두 라인 거부(전용 ErrorMessage 상수까지)는 선제 구현

### 기존 메서드는 건드리지 않고 새 메서드만 추가 — 변경점 최소화 (2026-09-28, 보강 2 · 최근 11-05)
- 요청이 "메서드 하나 추가"면 기존 팩토리/변환과 조립이 겹쳐도 기존 메서드를 private 빌더로 추출·위임하지 않는다 — 통째로 추가해 diff 를 추가분으로만, 중복 제거는 "별도 리팩토링 가능" 제안만
- 조회 키가 바뀌어도 "키 목록 → 키별 결과 맵" 한 메서드 형태를 유지하고 키 타입만 교체(String → 조합 VO) — 둘로 쪼개 외부 응답 원본·보조 맵을 파라미터로 흘리지 않는다
- 기존 식을 고칠 때 줄 나눔은 원래 형태 그대로 — 린터 강제가 없으면 한 줄 식을 여러 줄로 나누지 않는다. 나누면 diff 가 산식 변경처럼 보인다
- **왜:** 기존 시그니처/흐름이 바뀌면 리뷰 범위가 요청 밖으로 커지고 동작 동일성을 다시 검증해야 한다

### 같은 판단·파싱은 기존 메서드·유틸 재사용 (2026-07-10, 보강 1 · 최근 11-02, 병합 1 · 최근 10-28)
- 같은 클래스의 다른 흐름에 같은 조회·분기(키 A 없으면 키 B)를 하는 private 메서드가 있으면 호출부에 새 분기 대신 그 메서드를 호출. 결과 키가 달라지는 후속 조회는 키를 재계산하지 말고 앞 단계 산출물(생성된 메시지 등)에서 꺼낸다
- 구분자 결합 식별자는 encode/decode 유틸(VO)이 있으면 재사용(규칙 한 곳), 없고 단순 결합이면 `substringBeforeLast`/`AfterLast` 인라인 — 파싱용 VO/parser 신설 금지. 가변부가 꼬리면 Last 변형, 파싱 방향은 그 선택이 아니면 깨지는 입력(`A_B_2`)으로 테스트 고정
- 구분자 결합 포맷을 여러 흐름이 만들면 조립은 한 곳 — 개념명 object(`{System}{Concept}No.of()`)는 VO 로 읽히므로 신설하지 않고, 형제 시스템마다 있는 `client/{system}/util/{System}Constants` object 에 `private const` 구분자 + `generate{Concept}(a, b)`. 파싱 함수는 되돌려 읽는 곳이 생길 때만
- **왜:** 같은 판단이 두 진입점에 갈라지면 한쪽만 고쳐지고, encode 와 parse 가 어긋난다

### Spring·라이브러리 동작 함정 — 컴파일·mock 으로 안 잡히는 것 (2026-04-21, 병합 1 · 최근 11-10)
- **프록시 자기 호출:** 같은 클래스 안 `this.asyncMethod()` 는 프록시를 우회해 동기 실행 — 별도 클래스로 분리해 DI 로 호출. `@Transactional`/`@Cacheable` 등 프록시 기반 어노테이션 동일(Spring AOP 는 프록시를 통해서만 적용)
- **`@RequestParam` 의 Kotlin default 무시:** Spring MVC 는 reflection 으로 모든 파라미터를 채워 invoke 해 default 합성 메서드를 거치지 않는다 — `@RequestParam(required = false) param: T?` + 본문 `param ?: 기본값`, 또는 `defaultValue = "..."`(String 만). Kotlin default 와 `?:` 병기 금지
- **`ExceptionUtils.getRootCause()`:** cause 체인이 없으면 null 이 아니라 throwable 자신을 반환 — cause 가 진짜 있을 때만 채우려면 `ex.cause?.let { }`. "cause 없으면 null" 가정은 dedup 키/알림 필터를 빗나가게 한다
- **`@ConfigurationProperties` kebab/camelCase 경계:** Binder 는 camelCase 경계로 element 를 나눠 비교 — `fooBarId`(foo-bar-id)와 YAML `foobar-id` 는 element 수가 달라 매칭 실패(default/null). `@Name("foobar-id")` 로 바인딩 키 명시(Spring Boot 3.0+), lowercase 우회 금지. 바인딩이 안 되면 camelCase 경계와 YAML 키 비교부터
- **`@GetExchange` 는 POJO 를 쿼리 파라미터로 못 펼침:** `@RequestParam request: SomeDto` 는 `ConverterNotFoundException`, 무어노테이션 POJO 는 `No suitable resolver`(런타임에야). 필드별 `@RequestParam("외부키") 도메인명` — 쿼리 키는 `@RequestParam` value 가 결정(`@JsonProperty` 는 바디용), `List<String>` 도 반복 파라미터로 전개. 복합 객체를 단일 쿼리 값으로 보내는 특수 API 만 customArgumentResolver. 서버측 `@GetMapping` 의 ModelAttribute 바인딩과 혼동하기 쉽다
- **Map Bean 주입의 `@Qualifier`:** 같은 `Map<K, V>` 타입 Bean 이 유일하면 생략(타입 매칭), 여러 개 등록 가능하거나 흔한 타입일 때만 명시, 주입 전 동일 타입 Bean grep — 무조건 명시하면 Bean 이름 변경 시 잘못된 매핑이 늦게 발견된다

### 파라미터는 호출자가 가진 구체 값만 — 파생값·하드코딩·공용 검증 금지 (2026-04-22, 보강 3 · 최근 11-02, 병합 1 · 최근 10-28)
- 다른 파라미터나 원본 객체에서 유도 가능한 값(channelType → brand/client)은 넘기지 않고 소비 메서드가 도출 — 순수 파생(무비용)은 원본에 요구, 저장소 조회가 필요한 공유 데이터만 바깥에서 한 번 계산해 전달
- 상위 타입(brand) 대신 호출자가 가진 구체 타입(channelType)을 받고, 메서드 내부 채널 상수 하드코딩 대신 파라미터로
- 사용자 입력 범위/유효성 검증(최대 24시간 등)은 그 입력의 진입점(Admin Controller)에만 — 고정 윈도우 호출(Scheduler)·공용 Service 로 내리지 않는다
- 서비스 간 API 계약의 아이템 식별자도 같다 — 호출측(어댑터)이 가진 키(sku)로 받고, 호출측이 수신측을 먼저 조회해 내부 id 를 알아내 보내는 계약을 만들지 않는다. 수신측에 같은 개념의 기존 매칭 기준(외부 아이템 id 없는 채널을 sku 로 매칭)이 있으면 그 키로 통일
- 모듈 간 포트(`{Domain}Writer`)의 생성 메서드는 유스케이스 전용(`create{Usecase}{Domain}`, 내부에서 타입 고정)이 아니라 범용 `create(…, type: {Domain}Type, …)` — 타입은 호출자가 넘기고, 타입별 분기(취소 수량 검증·즉시 환불 타입)는 기존 overload 규칙을 그대로 일반화
- **왜:** 불필요한 매개변수는 값 불일치 버그를, 하드코딩은 재사용 불가를, 공용 경로 검증은 고정 호출의 불필요한 제약을 만든다

### 리팩토링·방식 변경 후 잔재 점검 — 중간 변환의 목적 재검증, 종속 요소 dead 여부 (2026-05-18, 보강 3 · 최근 11-10, 병합 1 · 최근 10-27)
- 원본의 중간 변환(Pair 묶기/평탄화/mapNotNull)은 각각 목적이 있다 — 입력 구조가 단순해졌으면 목적이 자동 달성/무의미해졌는지 확인 후 제거("이 변환이 없으면 결과가 달라지는가?"). 반대로 단순화 뒤 티켓 핵심 요구 로직(옵션별 수량 분배 등)이 함께 빠지지 않았는지 요구사항 대비 확인
- 바인딩/직렬화 방식을 바꾸면 종속 어노테이션(`@JsonProperty` 등)이 여전히 의미 있나, 클래스가 검증만/값 보관만 하는 껍데기가 됐나 — dead 면 제거/인라인
- 환경 분기(`isProd()` 게이트, 오픈 시 제거 todo) 경로 삭제·미사용 메서드 삭제 요청도 동일 — 그 경로에서만 쓰이던 메서드·오버로드·전용 프로세서·테스트 컨텍스트·ErrorMessage 상수, 참조가 사라진 DTO 파일·import 까지 호출 그래프로 추적해 같은 티켓에서 한 번에 삭제하고 목록을 보고한다. 지울지 되묻지 않는다
- **왜:** 리팩토링은 이동이 아니라 새 구조에 맞춘 재정리 — 잔재는 dead code 를 쌓고 "어디가 실제 매칭인지" 흐린다

### 호출처가 하나뿐인 로직은 private 추출 대신 인라인 — private 추출 기준의 단일 본체 (2026-08-12, 보강 8 · 최근 10-29, 병합 1 · 최근 10-16)
- 한 번만 쓰이는 블록(try/catch·검증 덩어리·응답 검사·두 갈래 분기·변환)은 가독성 목적으로 private(`toXxx`) 추출하지 않고 로컬 val·인라인. 추출 기준은 ①중복 3건 초과 ②독립 책임 ③별도 테스트 진입점 — 블록 크기가 아니라 재사용 실재
- "호출처"는 소비 메서드 수 기준 — 한 메서드 안에서 같은 빌더 조립을 분기별로 2~3번 반복해도 재사용이 아니다. 두 번째 소비 메서드가 생기면 추출, 이름이 겹치면 람다 파라미터를 구체화(`request` → `{xxx}Request`)
- 분기용 추출 금지: `else` 회피 가드, 전환기 이중 소스 분기, 데이터 객체가 할 판정(전송 대상 필터)을 Processor private 술어로 선행 — 분기는 인라인 `if / else`. 팩토리 한 곳용 계산(수량 분배 맵)의 private nested VO 도 금지 — `of()` 안 로컬 val 로 "검증 → 분배 → 조립"
- 예외(②독립 책임): (a) 브랜드/법인 한정 후속 정책 — 호출부엔 조건 + 호출 한 줄 (b) 본 흐름과 동떨어진 운영 정책 판정(prod/비prod × 테스트 마커) — 술어 `isXxx`·행동 `verbXxx` 각각 private, 호출부는 `if (this.isXxx(x)) 본 흐름 else this.verbXxx(x)` (c) 자체 조회·조기 반환·외부 알림·예외를 모두 가진 검증 덩어리는 `validateXxx` private + 호출부 조건 한 줄
- **왜:** 단일 호출처 추출은 흐름을 두 곳으로 흩을 뿐 추상화가 늘지 않는다
