# 예외·에러 메시지·데이터 무결성

> 읽는 때: 예외·ErrorMessage·외부 코드값 enum·필드 매핑·입력 검증을 다룰 때. 색인은 `index.md`.

### 확실하지 않은 필드는 데이터로 설정하지 않는다 (2026-05-06, 보강 2 · 최근 10-29, 병합 1 · 최근 10-28)
- 메시지/이벤트/외부 전송 시 의미가 불확실한 필드는 매핑하지 않는다 — "비슷해 보이는" 외부 필드를 채우지 말고 명확한 최소 필드만. 금액 필드도 0 placeholder 금지, 답이 없던 금액은 한 줄 재질문(도메인 규칙으로 계산될 수 있다)
- 외부 응답에 같은 의미로 해석 가능한 필드가 여럿(top-level summary vs nested)이면 자동 우선순위 판단 금지 — 옵션 표(위치/타입/의미 추정/티켓 일치)로 결정 위임
- 두 후보를 폴백 체인(`A ?: B`)으로 엮는 것도 자동 우선순위 판단 — 기본값은 실응답에 채워지는 필드 하나의 1:1 매핑(사유 상세가 비고 사유명만 오면 사유명), 나머지 후보는 DTO 필드로만 두고 보고에 대안 한 줄
- **왜:** 잘못된 매핑은 추적 어려운 오염 — 비어있는 편이 낫고, 미묘한 의미 차이는 운영 맥락을 가진 사용자가 결정한다

### 외부 코드값 enum — 도입 기준·코드 매핑·description (2026-04-27, 보강 5 · 최근 10-29, 정정 1 · 최근 10-29, 병합 1 · 최근 10-27)
- 외부 코드값은 문자열 리터럴 대신 code 프로퍼티를 가진 enum 으로. 단 ①다른 곳 재사용 ②외부 직렬화 ③타입 안전성이 필요한 호출 지점이 모두 없고 응답 DTO 한 곳의 추출 메서드에서만 쓰는 2-3개 매핑이면 DTO 내부 `when`
- 외부로 직렬화할 때만 `@JsonValue`/code 매개변수, 내부 분류 전용이면 companion `fromCode()` — 단순 1:1 이고 코드값이 enum 정체성과 강결합이면 매개변수 + `entries.firstOrNull { it.code == code } ?: throw`. 형제 enum 의 code·`@JsonValue` 구조를 옮기기 전에 데이터로 확인해 외부 코드가 enum name 과 같으면 code 프로퍼티 없이 `description` 만, 판정은 `it.name == code`(형제 enum 선례) — 같은 값을 두 번 관리하지 않는다
- 응답 DTO 의 코드 필드 타입은 enum 이 아니라 `String?` — 미지 코드 하나가 응답 전체 역직렬화를 깨면 안 된다. 판정 전에 companion `from(name: String?)`(형제 enum 의 nameMap 구조, 미지 값은 `ErrorMessage.Common.INVALID_ENUM_NAME`(클래스명·입력값) ClientException — 전용 상수 신설 금지)으로 enum 으로 바꾸고 인스턴스 술어(`isXxx()`)를 부른다 — 문자열 그대로 `==` 비교해 미지 값을 false 로 흘리는 술어는 silent 에러 지점
- `description: String` 으로 한국어 의미(`{CODE}("판매중")`) — 운영/디버깅/로깅용. 운영자가 고르는 Admin API 파라미터가 외부 상태값이면 Swagger `description` 에도 상태마다 '외부 정의 + 우리 처리 결과'
- **왜:** 리터럴은 오타·컴파일 검증 부재, 외부 코드는 의미가 안 보인다. 반대로 한 곳용 매핑의 enum 분리는 데이터와 매핑 표를 분산시킨다

### 예외 타입은 원인 주체 기준 + 도달 불가 추정 분기도 명시적 fail-fast (2026-04-16, 보강 3 · 최근 11-03, 병합 2 · 최근 10-28)
- `ClientException`(400) / `NotFoundException`(404) / `ServerException`(500) / `ExternalInterfaceException` — `.of(message = …)`. when `else` 의 빈 블록/"발생하지 않음" 주석 금지 — 명시적 throw, 메시지에 도달 입력값
- 원인 주체별: 호출자 잘못 `ClientException` / 서버 매핑·가정 붕괴 `ServerException` / 외부 응답 변환·검증 실패(옵션 타입 미지원·전달 id 부재) `ExternalInterfaceException`, 내부 시스템(PIM) 응답 검증은 `ServerException`. "찾지 못함"이라도 원인이 클라이언트가 보낸 값이면 404 대신 400 + 메시지에 요청값·기준값 양쪽 수치
- 호출자가 사내 시스템(어댑터 → 코어 내부 API)이어도 같다 — 요청이 가리킨 키(sku)가 우리 데이터에 없으면 호출자 잘못 `ClientException`(400), 사내 호출이라고 `ExternalInterfaceException`(502) 을 쓰지 않는다. 같은 ErrorMessage 를 던지는 형제 코드의 예외 타입이 기준
- 여러 행에서 값 하나를 골라낼 때 `singleOrNull` 금지 — 2건 이상이어도 null 이 돼 데이터 이상을 숨긴다. 값을 먼저 꺼내(`mapNotNull { it.x }` — 엔티티 `distinct()` 는 id 기준이라 값 중복을 못 거른다) `distinct()` 한 뒤 0개면 null, 1개면 그 값, 2개 이상이면 식별자와 찾은 값 목록을 담아 예외
- **왜:** 묵시적 통과는 silent fail — fail-fast 가 알람·추적·가정 재검토를 가능케 하고, 404/400 은 운영 알림 분류와 클라이언트 대응을 가른다

### ErrorMessage 상수와 예외 메시지 — 재사용·식별자·행위 (2026-06-02, 보강 3 · 최근 11-02, 병합 1 · 최근 10-28)
- 에러 메시지 리터럴 금지 — `ErrorMessage` object 의 도메인별 inner object 에 const(`{DOMAIN}_{ERROR_TYPE}_{DETAIL}`), 추가 전 같은 도메인을 grep 해 의미가 같으면 재사용(wording 이 한정적이면 일반화), 정말 다른 의미일 때만 신규
- throw 시 핵심 식별자(orderNo) + 발생 맥락을 메시지에 — const 의 `{0}` + `format`. ServerException 은 errorCode 가 전부 default 라 message 가 유일한 식별 수단. 같은 "부재/실패"가 여러 작업에서 나면 상수명·메시지에 행위(`XXX_{행위}_NOT_FOUND`)
- 재사용 기준은 "같은 엔티티 부재" 가 아니라 "같은 행위 중 부재" — 엔티티 도메인의 범용 부재 상수(`Order.…_NOT_FOUND_…`) 재사용 ❌ → 행위 도메인에 행위를 담은 상수(`Claim.CLAIM_{행위}_…_NOT_FOUND`, 메시지에 행위 + 식별자) 신설. 범용 상수로 "어느 처리 중" 이 메시지에서 사라지면 정정 대상
- 운영 로그를 조회할 수 없는 서비스(코어 등)에선 `log.error` 대신 증거 채널인 Slack 알림 메시지에 식별자·사유
- **왜:** 의미 중복 const 는 운영 알림에서 같은 사유를 두 메시지로 분산시키고, 식별자·행위 없는 메시지는 어느 주문/흐름인지 못 가린다

### 다건 외부 호출 에러 — 검증·응답 실패 모두 항목별로 모아 끝에 1회 throw (2026-06-12, 정정 1 · 최근 10-23)
- 검증 에러(입력 누락/도메인 규칙/매핑 부재)도 응답 실패도 즉시 throw 하지 않는다 — 항목 단위 `try/catch` 로 errors 에 "식별자 : ex.message" 를 쌓고 계속 처리한 뒤 끝에 join 해 1회 ExternalInterfaceException, 사유별 ErrorMessage 분리는 유지
- `@Async` 전송의 "매핑 없음" 건너뜀도 로깅 유틸의 미처리 WARN 으로 끝내지 않고 errors 에 합쳐 throw — Service aspect 가 비동기 예외를 GELF 로 남겨 알림 룰 대상이 된다
- **왜:** 한 항목 실패가 나머지 전송을 막으면 안 되고, 실패는 모아야 운영이 한 번에 조치한다

### 외부·레거시에서 가져온 값은 출처 검증·명시 (2026-05-04, 보강 1 · 최근 08-12, 병합 1 · 최근 10-28)
- 레거시 enum/매핑 값은 출처 파일 명시 + 타 프로젝트 교차 검증 + 공식 문서/운영팀 검증 권장, "검증된 source 가 한 곳뿐" 같은 한계도 보고
- 수치 제약 상수(최대 건수/chunk size)는 출처(스펙 원문/티켓/실측)를 보고에 명시, 못 찾으면 "출처 불명". 같은 계열 API 의 기존 상한과 다르면 그 불일치도 한 줄
- 타 프로젝트에서 aspect/interceptor/scheduler 를 복붙하면 MDC `application` 값·topic·slackChannel 같은 hardcoded 식별자를 grep 전수 검증 — logging aspect 는 모든 경로의 fan-out 지점이라 한 곳의 잘못된 값이 모니터링 전체를 오분류시키고 컴파일/테스트로 안 잡힌다
- **왜:** 레거시 값은 outdated·오류 복제 가능성이 있고, 출처 없는 값은 조정 가능 여부를 아무도 판단 못 한 채 굳는다

### 무결성 중요 도메인의 비정상 입력은 보정 말고 경계에서 명시 거부 (2026-08-20, 보강 3 · 최근 11-06, 정정 1 · 최근 10-19)
- 재고·금액처럼 틀리면 실피해가 나는 도메인에서 정상 클라이언트가 만들 수 없는 입력(중복 항목)은 합산/덮어쓰기로 관용하지 않고 경계(요청 객체 init)에서 ClientException 즉시 거부. 어겨져도 실피해 없는 "이론상 깔끔함" 검증은 오버스펙
- 외부 응답이 라인 합계만 주면 단가 = 합계 ÷ 수량(채널 할인 반영) — 카탈로그 정가 대체 금지, 나누어떨어지지 않으면 반올림 대신 식별자 포함 예외
- 금액 라인 구성(라인별 환불 금액·배송비·부호)은 규칙 문구(포함관계 등)를 모든 라인에 기계 적용하지 않고 실제 숫자로 검산 — 라인 환불 금액 합 = 고객이 실제 받는 돈, 하류 전송의 헤더·아이템·결제 합 일치. 고객이 별도 수단으로 낸 돈을 기록하는 라인의 환불 금액은 0
- 필수값 검증 범위는 '그 값이 실제로 부여되는 단위' — 채널·환경 술어는 1차 필터일 뿐, SKU 단위로 부여되는 시리얼은 출고 시 저장된 productCode 만 대상. 범위 안에서 하나라도 비면 외부 조회 전에 빠진 식별자 목록과 함께 거부, 범위 밖은 통과 — 채널 전체에 걸면 시리얼 없는 제품이 섞인 실데이터에서 깨진다
- **왜:** silent 보정은 클라이언트 버그를 숨긴 채 데이터를 오염시킨다 — 검증 채택 기준은 "통과 시 실피해 크기"
