# 도메인 로직·분기·조회

> 읽는 때: 판정·분기·조회·이벤트 발행 로직을 쓸 때. 색인은 `index.md`.

### 데이터 기반 로직은 해당 객체 내부에 배치 (2026-04-22, 보강 8 · 최근 10-26, 병합 1 · 최근 10-28)
- 데이터로 판단하는 로직은 그 데이터를 가진 객체에(`Xxx.ofTotalQty()`·enum companion), 외부 companion 의 resolve 금지. A·B 가 모두 데이터를 가지면 **판정 결과의 소비자**가 기준 — B 생성에만 쓰이면 `A.derivedX()` 대신 `B.from(inputs)` 안에서, 소비자가 여럿이거나 A 의 상태 의미가 생기면 A 로. 파생 메서드 제거 시 전용 테스트도 제거
- `XxxRequest.of()` 는 호출자가 손에 든 값(응답·id 목록·수량)만 받아 내부 VO 를 스스로 조립(내부 전용 nested VO 는 `private`)하고 전송 대상 필터도 안에서 — 대상 없으면 `null`, 호출부는 `?: return` 만
- 외부 응답 검증은 응답 객체 메서드로 — 값을 돌려주는 `requireXxx()`(없거나 타입 불일치면 예외)와 검증만 하는 `validateXxx(입력)` 분리, 팩토리는 순서대로 호출만
- 하위 아이템 갱신: 서비스는 메시지→VO 변환과 "갱신할 데이터가 있는가" 가드만, 탐색·수량 검증·불일치 예외는 애그리거트 내부에. 다른 애그리거트 데이터와의 비교 검증·알림은 그 데이터를 읽은 서비스에서 예외 직전에
- 읽기 모델(`XxxRead`)도 소유자 — 서비스가 `reads.flatMap { it.items }.filter { … }` 로 거르지 않고 Read 의 조회 메서드(`getXxx()`)를 부르며, 분기·조회 전에 맵/리스트를 로컬 val 로 빼지 않고 소유 객체 술어(`detail?.hasXxx()`)로 바로 묻는다
- nested config data class 는 데이터 컨테이너로, Map 조회 후 없으면 예외 던지는 메서드는 외곽 properties/config 본체에 모아 단일 진입점(파생값 `channelType.brand` 는 내부 도출로 위임)
- **왜:** 로직이 데이터와 분리되면 중복·다중 수정 지점이 생기고, 단일 소비자용 파생 메서드는 쓰이지 않는 API 만 노출한다

### 이벤트 발행 데이터 — 실제 변경된 영속 엔티티 기준, 전이·부가 갱신 순서는 스냅샷 의존으로 (2026-08-20, 정정 1 · 최근 10-16, 병합 1 · 최근 10-28)
- 변경 후 발행하는 이벤트 페이로드는 요청 파생값이 아니라 DB 에서 조회한 실제 변경 엔티티 목록에서 도출 — 이벤트는 "일어난 일"의 기록
- 한 트랜잭션에서 상태 전이(`ship()`)가 `registerEvent` 로 아이템 스냅샷을 복사해 발행하고 그 메시지에 부가 데이터(시리얼)가 실려야 하면 **부가 갱신을 먼저**, 의존이 없으면 상태 전이를 먼저(읽는 순서 = 중요도). 부가 갱신의 검증 예외는 그대로 던진다 — 같은 트랜잭션이라 함께 롤백
- 순서를 정하기 전에 전이 메서드가 등록하는 이벤트의 필드를 확인한다 — 확인 없이 '상태 먼저' 로 가면 메시지에 부가 데이터가 빠진다

### 채널/타입/상태별 분기는 단순한 when 우선 (2026-05-06, 보강 5 · 최근 11-10, 병합 1 · 최근 10-28)
- 호출부 `when (type)` 우선, 시스템 분리가 명확해지면 `Map<Type, Service>` Bean dispatch. 미구현 채널은 `// TODO. {채널명} 처리 구현 필요`(로그/예외 X)
- 같은 채널이라도 브랜드마다 쓰는 외부 API·상품 구조가 다르면 `when (channelType.brand)` 로 가른다 — 조회 데이터의 유무(채널 상품 id 가 있나, 옵션 매핑이 있나)로 경로를 고르지 않는다. 브랜드별 처리가 한눈에 읽힌다
- 입력 상태로 갈리는 흐름은 early-return 가드 체인 대신 `when (status)`, `else` 는 fail-fast. 분기 주체는 입력의 명시 상태 필드 — 다른 필드의 null 여부·추가 조회로 추론하지 않고, 특정 상태의 존재도 "A 없음 && 전체 존재" 대신 직접 조회
- 선행 단계(A) 누락을 후행 상태(B)로 보정할 때는 `A, B ->` 한 분기 + 진입부 "이미 처리된 흔적" early-return(후행 상태에만). 흔적은 외부 상태 조회 API(송장 존재), 없으면 처리 완료 시 삭제되는 내부 레코드 잔존 여부
- 분기 결과를 중간 리스트에 모아 루프 뒤에서 다시 돌지 않는다 — 묶음 전송 이득이 없으면 분기 안에서 조회·전송(항목 단위 try/catch)까지. 분기 조건은 `x?.hasXxx() ?: false`, 분기 전용 파생값은 사전 `val` 대신 분기 안에서
- 프로세서의 특정 상태만 제외할 때 `supports(brand, channel)` 에서 채널을 빼지 않는다 — 그 상태 분기 진입부에 `{STATUS}_EXCLUDED_CHANNELS` + early-return, 형제 프로세서(교환↔반품)도 동일. 지원 채널 제거는 다른 상태까지 조용히 끊는다
- 분기 축은 결과 구성을 실제로 가르는 명시 필드 하나 — 상위 분류(귀책 등)를 enum 필드로 얹어 먼저 가르면 중첩 `when` + 안쪽 `else` 가 된다. enum `when` 은 `else` 없이 전 값 나열(미지원 값은 자기 분기에서 throw)해 새 값이 컴파일 에러로 드러나게 하고, 분기에 안 쓰이는 분류 필드는 넣지 않는다
- **왜:** 사전 Map dispatch 는 빈 구현체 부담, 추론 조건은 의도 복원을 강요하고, 중간 리스트·사전 val 은 흐름을 두 곳으로 흩는다

### 식별자 포맷 — 일관성 목적의 조합 금지, 유일성 목적의 조합은 값 자체에 (2026-07-21, 보강 1 · 최근 11-02)
- 외부 계약상 강제가 아니면 각 흐름이 실제 가진 값에서 가장 단순하게 도출 — "일관성"을 위해 없는 값을 조인/변환해오지 않는다. 자문: "외부 계약의 요구인가, 내 일관성 강박인가"
- 외부 번호가 우리 처리 단위(배송)보다 넓은 단위(주문)로만 유일하면 저장 키 재설계(SK 조합)·수신측 멱등 판정 변경 대신 저장·전송하는 식별자 값 자체를 `{처리단위키}_{외부번호}` 로 조립 — SK·코어 멱등·중복 검증 등 모든 소비처가 변경 없이 단위별 유일을 얻는다. 적용 전 그 값을 되돌려 파싱하거나 외부 재조회 키로 보내는 흐름(반품·교환 등)을 전수 조사해 제외

### 조회는 필요한 단위에 맞는 API 로 — 다건은 IN절 배치, 단건은 단건 조회 (2026-07-21, 보강 3 · 최근 10-30, 병합 1 · 최근 10-28)
- `ids.map { getById(it) }`(N회) 금지 — 리포지토리 `findAllBy{Key}In(keys)` 배치 조회 후 서비스의 private `get` 메서드로 래핑(단일 진입점). 재사용 의도의 공통 조회는 연관을 온전히 로드(`@EntityGraph`) — 한 호출처 최소 필요로 좁히면 다른 재사용처에서 N+1/불완전 로드. 메서드명은 기존 리스트 반환 네이밍(`findAllBy…`)에 통일
- `getXxxs(상위키).firstOrNull { }` 대신 단건 `getXxx(id)`(없으면 추가 고려), not-found 는 클라이언트 에러 핸들러에 위임. 2단계 조회(매핑 → 상세)의 상세 입력은 1단계 응답 전체가 아니라 요청 건과 정확히 매칭된 키만
- 대상 건 처리 흐름(확정 등)은 그 건의 키로만 묻는다 — 형제 수집 흐름의 '채널 전체 목록 조회 → 메모리 필터' 를 복제하지 않고 PK+SK 단건 존재 확인(`isExist{X}`). 외부 API 에 대상 한정 파라미터(라인 순번 목록 등)가 있으면 응답을 메모리에서 거르지 말고 요청에 담는다 — 빈 값이면 전체가 오는지 실측해 보고
- **왜:** N round-trip → 1쿼리, 목록+필터는 불필요한 페이로드 + not-found 이중화

### QueryDSL — projection 은 constructor + Result data class, 애그리게이트 걸친 집계는 코드에서 (2026-09-23, 병합 1 · 최근 10-28)
- `Projections.constructor({Result}::class.java, …)` + `{module}/repository/result/` 의 `data class {Xxx}Result`, `@QueryProjection` 미사용(엔티티/컴파일 결합 회피). result 필드는 실 컬럼 nullability 그대로, 기본값 없음
- 다른 애그리게이트를 걸치는 집계는 `JPAExpressions` self-join/상관 서브쿼리로 한 쿼리에 넣지 않는다 — 리포지토리는 매칭 행만, 각 Reader 로 raw 조회 후 Facade/코드에서 집계. alias 는 메인 쿼리와 겹치지 않으면 static Q, self-join 등 불가피할 때만 별도
- **왜:** projection 은 조회 스키마의 투영, 상관 서브쿼리는 읽기·테스트·수정이 모두 어렵다

### 상태/조건 판정은 도메인 술어로 — 원시 술어 + 호출 결정은 이름 붙인 메서드 하나 (2026-07-28, 보강 3 · 최근 10-16, 병합 1 · 최근 10-28)
- `x.status == SPECIFIC_VALUE` 대신 기존 술어(enum companion `canXxx`/`isXxx`) 재사용, 없고 반복되면 신설. 정확한 단일값 매칭이 도메인상 필수일 때만 인라인
- 술어 이름은 비교 구현이 아니라 객체의 검증 행위로, 같은 애그리게이트의 기존 형태(`hasMismatched~`/`is~`)에 맞춘다. 흐름 게이트 술어는 그 흐름의 행위(확정 흐름이면 `isConfirmable`, 인접 흐름 어휘 `isCollectable` ❌)
- 본문은 사실 판정만 — "빈 입력이면 false" 같은 정책 분기는 호출 흐름 진입점 한 곳에. 채널 한정 기능은 `ChannelType.isXxxChannel()` + companion EnumSet, 미오픈 기능은 술어 안 `!isProd()` 게이트 + `// todo(이름). 오픈 시 prod 에서도 활성화`
- 상태 조합 술어(`isWaitingXxx` = 타입 조건 && 미발급)보다 원시 술어(`hasXxx`/`isXxxAutoIssued`)를 두고, 변환(`toXxx`)은 다른 필드 조건으로 전체를 가드해 null 을 돌려주지 않고 각 필드를 있으면 매핑·없으면 null 로 채운 객체 반환. 호출부가 같은 객체의 술어 둘을 `&&` 로 엮으면 그 결정에 이름을 붙인 메서드 하나(`is{Decision}()`)를 객체에 두고 호출부는 그것만
- **왜:** 판정 규칙이 한 곳에 응집돼야 기준 변경 시 술어만 고치고, 호출부에 흩어진 조건은 판정 의미를 잃는다
