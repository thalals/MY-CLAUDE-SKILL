# QA 테스트 시나리오

> 읽는 때: 테스트 시나리오·체크리스트 문서를 쓰거나 실 데이터로 검증할 때. 색인은 `index.md`.

## 테스트 시나리오 검증 프로세스

### 실 데이터 기반 시나리오 검증 + 체크박스 체크 기준 (2026-05-15)
- 사전 작성된 시나리오는 실 응답/운영 데이터로 매칭 검증: ①실 데이터를 채널/필드별 분류 ②각 테스트 케이스를 실 데이터로 매칭 시도 ③매칭 근거(채널/건수/필드값)를 답변에 명시한 항목만 체크
- `- [x]` = 실 sample 매칭 또는 코드 로직 동작 확인됨 / `- [ ]` = 운영·에러 주입·재호출·대량 데이터 등 sample 만으로 검증 불가. 의심스러우면 unchecked 유지
- 운영 검증이 필요한 항목(대량 데이터 한계, 자정 경계, 페이지네이션)은 sample 만으로 절대 체크 X
- **Why:** 시나리오는 가정이고 체크 = 사실 보장 — 추측 체크는 검증 신뢰도를 무너뜨린다

### 시나리오와 실 데이터 불일치 시 시나리오 정정 (2026-05-15)
- 테스트 케이스 라벨 / 예시값이 실 데이터와 맞지 않으면 실 데이터 기준으로 시나리오를 수정한다
- 예: 라벨이 `[A채널]` 인데 실 데이터에선 A채널이 빈값이고 패턴이 `[B채널]` 에 등장 → `[B채널]` 로 라벨 정정 + sample 출처 부가 설명
- 사용자 피드백: "테스트 시나리오 중 실제 데이터와 맞지 않는건 맞춰서 테스트 케이스를 수정해줘"
- **Why:** 잘못된 라벨/예시로는 검증을 해도 의미가 없다. 시나리오의 정확성이 검증보다 먼저.
- **How to apply:** 검증 중 라벨/예시값이 실 데이터와 어긋나면, 데이터 기준으로 수정. 변경 사유와 sample 근거를 답변에 정리. 범위 차이가 있으면 (예: 5자리만 등장, 6자리 없음) 검증된 부분만 ✅ + 미등장 부분은 별도 항목으로 분리.

### 검증 중 발견된 신규 의문점은 별도 항목으로 (2026-05-15)
- 검증 중 코드 가정 vs 실 데이터의 불일치 같은 신규 의문이 발견되면, 기존 항목 수정이 아닌 별도 검증 항목 신설
- 예: 코드 주석의 가정 (예: "첫번째 응답값은 스펙 정의이므로 drop") 이 실 응답과 어긋남 → `⚠️ 가정 재검증` 항목 신설
- **Why:** 기존 항목 안에 묻으면 발견 자체가 사라진다. 별도 항목으로 떠야 추적/조치 가능.
- **How to apply:** ⚠️ 마커 + 발견된 사실 + 영향 (silent 버그 가능성 등) + 후속 조치 권장.

### 테스트 시나리오 단위 필요 샘플 건수 산정 — 시나리오 매트릭스 + 분리/결합 옵션 (2026-06-12)
- 작성된 테스트 시나리오 문서를 기반으로 "필요 샘플(주문/주체) 건수" 를 산정할 때 시나리오 단위로 매트릭스 작성 + 분리/결합 두 옵션 같이 제시
- 절차:
  1. **시나리오 매트릭스** — 행: 시나리오, 열: 대상(채널/브랜드/카테고리), 셀: `1` 또는 `—` (미지원/제외)
  2. **카테고리별 소계** — 사용자 의도에 맞는 분류 행 (예: 정상/취소/반품/교환 등)
  3. **분리 합계** — 시나리오별 독립 샘플 필요 시 총 건수
  4. **결합 합계** — 같은 샘플에서 순차 진행 가능한 정상 흐름끼리 묶었을 때 단축된 총 건수
  5. 사용자 운영 환경 부담 시그널 (예: 실 운영 환경 영향) 이 있으면 결합 옵션 권장 표시
- 결합 가능성 판단:
  - 같은 샘플에서 순차 진행 가능한 흐름 → 결합 가능 (예: 정상 출고 → 정상 반품)
  - 분기 흐름 (다른 결과를 검증해야 함) → 분리 필요 (예: 정상 vs 철회 vs 미경과)
- 사용자가 카테고리 추가/제외 요청 ("X는 빼자") 하면 매트릭스의 해당 행만 제거하고 즉시 재산정
- **Why:** 시나리오 매트릭스 자체가 카운트 근거 — 표만 보면 어떤 시나리오가 어떤 대상에서 빠지는지 즉시 확인 가능. 분리/결합 두 옵션 제시는 사용자가 운영 환경 부담을 고려해 결정 가능하게 함. 카테고리별 소계가 있어야 추가/제외 시 즉시 재산정 가능
- **How to apply:** 건수 산정 요청 시 ① 시나리오 매트릭스 표 작성 ② 카테고리별 소계 행 추가 ③ 분리 합계 + 결합 합계 같이 제시 ④ 운영 환경 부담 시그널 있으면 결합 권장 ⑤ 카테고리 변경 요청 시 표만 수정해 즉시 재산정. 결합 옵션은 사용자 결정 위임 — 자동으로 결합 적용 X

## 테스트 문서 작성

### 추적 문서 부분 수정 시 대상별 동일 구조 + 기존 양식 일관성 (2026-06-12)
- 여러 대상(채널/브랜드/카테고리) 에 동일 시나리오를 추가할 때 각 대상의 sub-section 은 동일 구조로 작성 (헤더 형식, 시나리오 순서, 체크박스 라벨 패턴 통일)
- 기존 문서에 사용자가 이미 작성한 양식이 있으면 그 양식을 그대로 따른다 (인용 마커, 줄바꿈 방식, 들여쓰기 깊이, 라벨 prefix 등)
- 대상별 차이는 도메인 의미 있는 부분에만 한 줄로 명시 (예: "X 측 상태가 Y인 경우 ..." 처럼 대상 특이 wording 만 변경)
- 사용자 피드백 흐름: 비어있는 sub-section 4개를 채우는 작업에서 첫 번째 sub-section 의 기존 양식 (인용 → 시나리오 sub-list → 체크박스) 을 그대로 다른 sub-section 에 복제 → 사용자 짧은 칭찬 ("굳!")
- **Why:** 동일 구조는 ① 시각적 일관성 (sub-section 간 비교 시 차이만 한눈에) ② 검색/대치 작업 효율 ③ 사용자 작성 양식 존중. 임의 양식 개선은 사용자가 의도한 일관성을 깨뜨림. 차이는 도메인 의미가 있는 부분에만
- **How to apply:** 추가 작업 전 ① 기존 sub-section 1개의 양식을 정확히 파악 (들여쓰기 / 마커 / 라벨 패턴) ② 동일 구조 그대로 다른 대상에 복제 ③ 대상 고유 wording 만 1줄씩 변경 ④ 임의 양식 개선 (마커 변경, 줄바꿈 방식 변경) 금지 — 사용자가 명시 요청한 경우에만 양식 변경

### 티켓 테스트 케이스는 간결한 체크리스트 — 실행 단계와 확인 항목 구분·중첩 (2026-09-14, 보강 09-30)

- **무엇:** 티켓 테스트 케이스는 상세 분석 서술형이 아닌 간결한 체크리스트로 작성. 해야 할 것(실행 단계)과 확인해야 할 것(검증 항목)을 구분하고, 각 실행 단계 하위에 그 시점에 확인할 항목을 중첩 배치
- **왜:** 서술형은 테스트 실행 시 따라가기 어렵다 — 실행 순서와 각 시점의 검증 항목이 한눈에 보여야 빠짐없이 진행 가능
- 예시 구조:
  ```markdown
  - [ ] 1. <실행 단계 (예: API 호출)>
    - [ ] <이 시점에 확인할 것 (예: 응답 200, DB 상태 변경)>
  ```
- Jira 티켓(Atlassian MCP markdown)은 중첩 task list 가 드롭되므로 단계는 `**굵은 문단**`, 확인 항목은 그 아래 평탄 `- [ ]` 로 작성 — 단계/확인 구분과 순서 원칙은 동일하게 유지

## 하지 말아야 할 것

### 추적 문서 부분 수정 시 사용자 작성 부분 자동 교정/제거 금지 (2026-06-12)
- 사용자가 작성한 추적 문서를 부분 수정할 때 사용자 작성 부분은 "텍스트 내용" 뿐 아니라 ① 빈 placeholder (예: `- ` 빈 bullet, `[ ] ` 빈 체크박스) ② 미완성 라인 (`- [ ] X | ` 처럼 trailing whitespace) ③ 오타 (`받았을` 대신 `받앗을` 같은) 모두 보존
- search-and-replace 작업 시 사용자 작성 텍스트를 원본 그대로 매칭 — 자동 교정 X (오타를 정상 표기로 바꾸지 않음)
- 일부 추적 문서 도구는 부분 수정 후 normalize 동작으로 빈 placeholder 가 자동 제거될 수 있음 → 작업 후 변경 검증 단계에서 발견 시 사용자에게 즉시 보고 (의도 확인 후 복원 결정 위임)
- **Why:** 사용자 작성 빈 placeholder 는 향후 추가 시나리오 자리 표시일 가능성 — 자동 제거하면 의도 손실. 오타는 사용자가 문서 내 다른 검색/참조에 사용 중일 수 있어 보존이 안전. normalize 동작은 도구마다 다르므로 작업 후 의도치 않은 변경 발견 시 즉시 사용자 알림 필요
- **How to apply:** ① search-and-replace 의 old_str/new_str 는 원본 텍스트 그대로 사용 (오타 포함) ② 빈 placeholder 라인 (예: `- ` 만 있는 줄) 도 new_str 에 그대로 유지 ③ 작업 후 결과 비교 검증 — 빈 placeholder 또는 추가 라인이 사라졌으면 사용자에게 보고하고 복원 결정 위임
