# 검증·영향 분석·디버깅

> 읽는 때: 버그 원인 분석, 시그니처·타입 변경, 동작 확인이 필요할 때. 색인은 `index.md`.

## 더 신경써야 할 것

### 도메인 필드 타입/시그니처 변경 시 전수 영향 분석 (2026-05-15, 보강 1 · 최근 10-27)
- `grep` 전수 조사 후 6 카테고리로 점검: ①저장(DDL/@Column) ②검색(filter 메서드) ③표시(DTO/masking) ④이벤트 전파(Kafka 매핑) ⑤외부 송신 ⑥하위 컨슈머
- 빈 문자열 vs null 의미 차이, downstream 영향까지 3등급(안전/부작용/위험) 표로 정리
- 보강(10-27): 생성자 파라미터 순서 변경·중간 삽입처럼 같은 타입이면 컴파일이 통과하는 변경은 grep 만으로 "여기뿐" 이라 단정하지 않는다 — 별도 worktree 에서 대상 클래스를 임시로 깨뜨려(첫 파라미터에 `Nothing? = null` 추가, `data` 제거) 위치 인자·구조분해·`copy`·`componentN`·생성자 참조를 전부 컴파일 에러로 드러내고 main+test 를 컴파일한다. 이름 기반 매핑(Jackson·Fixture Monkey·리플렉션)은 컴파일 밖이라 따로 확인하고, 첫 보고부터 검증 방법과 한계를 함께 적는다
- **왜:** 한 곳 누락이 silent 버그 — 특히 이벤트는 타 서비스로 전파되어 발견이 늦다

### 버그/누락 수정 시 같은 문제를 가진 지점 전수 점검 — 같은 패턴 + 복수 진입점 (2026-06-24, 보강 2 · 최근 10-07)
- 같은 안티패턴이 여러 곳에 있으면 grep 전수 수집 → 각각 실제 깨지는지 확인(우회 코드/커스텀 리졸버 유무) → 깨진 것만 수정, 동작하는 동일 패턴은 이유와 함께 제외 보고
- 같은 개념(필드 세팅/검증/변환)을 다루는 다른 진입점(오버로드, API/consumer/이벤트 경로)도 같은 문제인지 점검 → 함께 수정하거나 범위 밖이면 보고
- 구조·스타일 피드백(예: 분기 기준을 목록 응답의 상태 필드로)도 받는 즉시 같은 클래스의 형제 지점(인접 메서드의 같은 판정·필터)에 전수 적용한다. 형제가 같은 저장소의 동일 역할 변환 함수(다른 채널의 같은 빌더)면 보고로 끝내지 않고 '같이 수정 / 별도 티켓' 옵션으로 올린다
- **왜:** 한 곳만 고치면 나머지 경로에 같은 버그가 silent 잔존하고, 표면 패턴만 보고 일괄 수정하면 정상 케이스를 깨뜨린다 — 전수 조사(빠짐 방지)와 케이스 검증(오작동 방지)을 동시에

## 잘한 것 / 유지할 것

### 디버깅은 단정 대신 측정 — 가설 우선순위 + 검증 수단 + 해석 분기, 외부 통합은 레이어별 (2026-05-11·05-15, 보강 05-13·10-07 ×2·10-28, 병합 11-10)
- ①가설 우선순위 정렬 ②가설별 복붙 가능한 검증 수단(쿼리/CLI/롤백 쉬운 진단 코드) ③결과 해석 분기("0건→A 확정 / ≥1→B") ④다음 단계 미리 정의
- 분산 시스템/인프라 의존 버그는 특히 측정 필수 — 측정 전엔 "가능성 높지만 측정 필요"로 표기. 코드 경로를 단언하기 전엔 grep 으로 호출/저장 경로 전수 확인
- 외부 응답 필드를 판정 기준(필터/스킵)으로 쓰기 전에 그 필드가 어느 상태·시점부터 채워지는지(상태 라이프사이클)를 확인한다 — 아직 비어 있는 상태의 정상 건까지 silent 제외된다
- "X 가 원인인가" 질문은 X 의 가부로 끝내지 않고 증상 값이 처음 만들어진 지점(발행부·형제 저장소)까지 역추적해 원인 체인(①발행 ②소비 ③증상)을 표로, X 가 아닌 근거는 "소비 측 입력에 X 가 들어오지 않음" 으로 갈라 제시
- "로직에 구멍이 있다" 는 전제의 질문은 첫 줄에서 ①가드가 설계대로 입력 오류(마커 오타·대소문자 불일치 등 합의 토큰 위반)를 걸러낸 정상 동작인지 ②비교 로직 결함인지 판정한다 — 정확 일치가 계약이면 완화(ignoreCase 등)는 수정이 아니라 정책 변경 제안으로 분리
- 외부 통합 디버깅은 레이어별로 한 단계씩 — 에러의 레이어(TLS/HTTP/인코딩/파싱/비즈니스 검증) 식별 → 그 레이어 가설 1개 → 도구(openssl/curl/로깅)로 검증 → 수정 → 다음 레이어 반복. 여러 레이어 동시 수정 금지(어느 것이 root cause 였는지 모르게 된다)
- **왜:** silent degrade 는 정상 케이스와 외관이 같아 측정 없이 못 가른다. 라운드트립당 한 단계씩 좁혀지고 사용자 검증 비용이 거의 0

### 토큰 한도 초과 검색 결과는 subagent 슬라이스 분석 (2026-06-12)
- 한도 초과로 파일에 떨어진 결과는 직접 읽지 않고 subagent 에 파일 경로/슬라이스 방법/찾을 키워드/반환 형식을 지정해 위임. 받은 인용은 원문 그대로 사용
- **왜:** 메인 컨텍스트를 보존하면서 핵심만 추출

### 라이브러리/런타임 동작은 throwaway 실측으로 검증 (2026-06-24, 보강 1 · 최근 09-11)
- 파싱·포매팅·예외 발생 여부·null 처리 등 미묘한 동작은 최소 케이스 throwaway 코드(프로젝트 실제 의존성 버전)로 실측 후 결론 (예: DateTimeFormatter `yyyy` vs `uuuu` + STRICT)
- 보강: 사용자가 제안한 표현/연산자도 추측으로 평가하지 않고 컴파일·실행으로 확인 후 답한다. 안 되면 "어느 오버로드가 잡혀 무슨 의미가 됐는지"까지 제시 — 컴파일은 되는데 의미가 반대인 경우가 가장 위험
- **왜:** 기억으로 단정하면 잘못된 진단을 사실처럼 보고하게 된다 — 실측 비용은 작다
