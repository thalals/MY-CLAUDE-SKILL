# 문서·기록·규칙 문서

> 읽는 때: 노션·Jira·Work Log·daily 기록·스킬·규칙 문서를 쓸 때. 색인은 `index.md`.

## 하지 말아야 할 것

### 대화 중 규칙 자동 추가 금지 — 스타일 파일·규칙 문서·메모리·문서 체계 구조 (2026-05-07, 보강 2 · 최근 11-05)
- `/collect-feedback` 호출 또는 "룰에 추가해" 명시 시에만 반영. 코드 수정과 룰 수정을 분리
- 스타일 파일 밖의 규칙 문서(기록 규칙 파일, 폴더 지도의 관리 규칙, 메모리)도 같다 — 일회성 요청을 처리하면서 재발 방지 규칙을 함께 써 넣지 않는다. 계속 지킬 뜻("앞으로"·"항상")이 보일 때만 규칙으로 적고, 필요해 보이면 보고 끝에 제안 한 줄
- 문서 체계의 구조(폴더 신설·분할·이동, 문서 종류)도 같다 — 자리가 없으면 자리를 지어내지 않고 구조 제안(왜·바뀔 모습·영향)을 세션을 넘어 남는 한 곳에 올려 확인 뒤 반영하고, 그때까지 그 내용은 보류한다. 매 보고에 열린 제안을 붙인다
- **왜:** 룰 반영 결정 권한은 사용자에게 있다 — 자동 반영은 의도치 않은 룰을 누적시킨다

### 대화/작업 기록 요청 — 정해 둔 형식이 있으면 그 형식, 없으면 원본 그대로 (2026-04-22, 보강 4 · 최근 11-05)
- 형식을 정해 두지 않은 "기록해줘" 요청엔 요약/재구성하지 않는다. 대화 원본이 필요하면 `/export` 안내
- 세션·오늘 대화를 daily history 에 남기는 요청은 사용자가 형식을 정해 둔 정리본이다 — 쓰기 전에 볼트의 `daily history/SKILL.md` 를 읽고 그대로 작성·병합하며 원문은 붙이지 않는다. 형식 규칙은 그 파일이 단일 소스라 여기 복제하지 않는다
- 기록에서 뽑아 쌓는 지식 문서(시스템 사전)도 형식은 그 체계의 규칙 파일이 단일 소스 — 원칙만 둔다. ①동작 사실은 대화 서술·README 가 아니라 현재 코드로 확인해 쓰고, 다르면 코드를 따르며 차이를 알린다 ②사용자가 정한 업무 규칙(정책)은 코드로 복원되지 않으므로 사실과 다른 자리에 모아 피드백이 쌓일 때마다 고친다
- ③검증에서 나온 불일치·미결 항목은 본문 사실과 따로, 판정 상태별 자리(의도된 제약·고칠 문제·아직 정하지 않은 것)에 둔다. 판정 전 항목은 답을 기다리지 않고 '정하지 않은 것' 에 기록하고, 판정이 나면 그 자리로 옮긴다(지우지 않음) — 섞이면 미결이 확정 사실로 읽힌다
- ④구조에서 가장 중요한 문서는 지도(색인)·용어집이다 — 데이터 문서를 같은 층에 섞지 않고 하위 폴더로 묶으며, 그 폴더에는 지도를 따로 두지 않고 상위 지도가 관리한다
- **왜:** 원하는 것은 원본이지 정리본이 아닐 수 있다 — 정리본은 사용자가 형식을 정해 둔 곳에서만 만들고, 여러 에이전트가 같은 구조로 쌓으려면 형식이 한 파일에만 있어야 한다

### 룰/피드백 문서는 self-contained 하게 — 세션 맥락·도구 종속 용어 금지 (2026-05-15, 병합 1 · 최근 11-10)
- 룰 본문에 프로젝트 고유 명칭·구체 클래스명·작업 케이스명 금지. 예시는 일반화된 placeholder(`List<A>`, `field`)로
- 룰만 단독으로 읽어도 언제/왜/어떻게 적용하는지 이해돼야 한다
- 특정 도구명 대신 "추적 문서", "테스트 시나리오 문서" 같은 추상 용어로 작성. 위치는 사용자가 링크/경로로 지정
- **왜:** 세션 맥락에 묶인 룰은 다른 작업에 적용하기 어렵고 명칭이 바뀌면 함께 outdated 된다 — 도구에 묶이면 도구가 바뀔 때 전부 재작성해야 한다

## 더 신경써야 할 것

### 노션 Work Log 작성 스타일 (2026-04-22)
- `/collect-worklog` 스킬로 작성, 상세 규칙은 스킬 파일 참조. 날짜 명시 시(예: 20260421) 해당 날짜 토글에만 작성
- 들어온 일 각 항목은 토글(요약 1문장 + 내부 번호 타임라인), 서술형(키워드 나열 금지)
- 사람 이름: 한국인은 직책+님. 슬랙 링크는 괄호로 `([슬랙](url))`

- 토글 병합/분리(case 단위)와 `update_content` timeout 대응 5단계는 `/collect-worklog` 스킬이 단일 소스 — 여기 복제하지 않는다

### 노션·티켓 문서 작성 스타일 (2026-04-16, 보강 1 · 최근 10-28)
- 참고자료 템플릿(entity 설계 문서 등)의 형식: 배경 → 내용/라이프사이클 → 액션 플로우(Mermaid) → Entity 설계 → Access Patterns
- Jira 티켓 완료 보고(리뷰어용)도 같은 골격 — 작업 내용 요약(불릿) → 엔티티 설계 표 → 생명주기(생성·사용·삭제 조건) → 액션 플로우 Mermaid → Access Patterns → 리뷰 포인트/후속 → 작업 코드 → 참고 자료. 티켓 템플릿 섹션(🛠️ 작업 내용 / 🧑‍💻 작업 코드 / 📎 참고 자료)은 유지하고 그 사이에 넣는다
- 후속 작업은 완료 보고의 후속 항목으로 끝내지 않고 사용자가 지정한 부모 티켓(원 티켓의 부모와 다를 수 있음 — QA 대응 티켓 등, 미지정이면 한 줄 질문)의 하위 티켓으로 건별 생성 — 유형은 부모 이슈 유형이 허용하는 하위 유형, 제목 접두·담당자는 형제 하위 티켓 관례, 본문은 같은 템플릿 3섹션(배경 한 문단 + 할 일 불릿 + 참고 링크), 생성 후 원 티켓의 후속 항목에 키를 연결
- 테이블 데이터는 plain text — 백틱 강조 금지, 인라인 코드는 본문 설명에서만 (04-16 "백틱 남용 금지" 룰 통합)
- Mermaid 다이어그램의 DDB CRUD 는 색상 블록 구분 ([C] 파랑, [R] 초록, [D] 빨강)

## 잘한 것 / 유지할 것

### 신규 스킬/룰 작성 — 직후 본인 절차로 dogfood 검증, 딸린 도구는 읽는 대상 옆 + 지도·스킬에 등재 (2026-05-15, 보강 2 · 최근 11-11)
- 만든 절차를 본인 케이스에 즉시 적용해 빠진 단계·모호한 표현을 발견. 자기 적용이 불가한 룰은 다음 실제 작업에서 시연
- 대화에서 좋았던 산출물 형식을 스킬로 만들 때는 템플릿만 옮기지 않고 그 형식이 좋았던 이유(실제 diff 기반, 실측·추론 구분 등)를 작성 규칙으로 넣고, 완료 보고에 방금 작업에 스킬을 적용한 출력 + 빠진 단계 유무 한 줄을 붙인다
- 스킬·기록에 딸린 도구(스크립트)는 작업 저장소가 아니라 그 도구가 읽는 것 옆에 둔다 — 기록 문서·규칙을 읽으면 규칙 파일 옆, 세션 기록을 읽으면 스킬 폴더(백업 규칙 대상). 만들거나 고치면 같은 편집에서 에이전트가 처음 읽는 지도·스킬에 용도·실행 시점을 한 줄 적는다. 도구로 옮길 것은 값 계산(시각 추출·커밋 대조·목록 대조)이고, 어느 문서가 자리인지 같은 의미 판단은 지도를 읽어 LLM 이 한다
- **왜:** self-application 가능 여부가 룰 명확성의 기준 — 등재하지 않은 도구는 다음 에이전트가 모른다
