# 요청 범위·해석

> 읽는 때: 코드·설정·문서를 고치는 모든 작업. 색인은 `index.md`.

## 하지 말아야 할 것

### 노션 문서 수정 vs 코드 수정 혼동 (2026-04-16)
- "수정해줘"는 문맥으로 판단 — 설계 논의 맥락이면 문서, 구현 단계면 코드. 애매하면 확인
- **왜:** 문서만 고치면 실제 동작에 반영되지 않는다

### 요청한 범위만 수정 — 과잉 대응 금지 (2026-04-20, 보강 3 · 최근 11-02)
- 수정 대상(코드/설정/환경)을 먼저 확인하고 지정한 범위 안에서만 작업한다.
- 버그 수정에 기존 데이터 보정(backfill)을 끼워 넣지 않는다 — 선택지에 올리더라도 '보정 안 함'을 포함하고 범위(DEV/PROD)만 묻는 식으로 보정을 전제하지 않는다
- 지정 대상 여러 곳 중 요청한 제거 대상(환경 분기)이 없는 곳은 '변경 없음 + 확인 근거(무엇을 grep 했고 왜 해당 없음인지)' 를 티켓에 기록하는 것이 기본값 — 겉이 비슷한 채널 특이 분기까지 제거로 넓히지 않는다
- 두 저장소에 걸친 작업에서 사용자가 한쪽을 todo 주석 placeholder 로 두라고 했으면 그 주석이 범위 경계다 — 상대 저장소 작업 승인도 승인 문구가 지목한 쪽만 하고, 내가 "연동까지" 를 묶어 제안해 승인받았어도 placeholder 해제·연동·테스트 수정은 같이 풀지 않는다. 저장소는 순차로 진행
- **왜:** 요청 밖 코드 변경은 사이드 이펙트를 만든다

### 사용자 표현의 외연을 추상화하지 않기 (2026-05-07, 보강 2 · 최근 11-10)
- "파라미터", "날짜와 시간", "default 값" 같은 표현은 가장 직접적인 표면 의미 그대로 채택. 추상화하고 싶으면 한 번 묻기
- 보강(11-10): 분류어로 지정한 대상("○○ 브랜드 채널")을 지금 작업 중인 채널 하나로 좁히지 않는다 — 그 분류에 속한 전부에 적용하고, 기존 동작이 바뀌는 대상은 환경별 영향 표로 보고한다. 좁혀 적용한 뒤 "나머지도 원하면 알려달라" 는 같은 지시를 두 번 하게 만든다
- 보강(11-02): "주석처리해줘" 는 그 호출을 주석 placeholder 로 대체하라는 뜻 — 기존 경로를 안전장치로 같이 살려두지 않는다. 걱정되는 영향은 보고 한 줄로
- **왜:** 우회 해석은 의도와 다른 구현과 인터럽트를 유발한다

### 타 환경 적용·레퍼런스 패턴을 그대로 쓰지 않기 — 현재 컨텍스트에서 도출 (2026-05-13, 보강 3 · 최근 11-05)
- 추천 단계: "dev 에 적용돼 있으니 prod 도 추천" 같은 mirroring 은 근거가 아니다 — 트레이드오프·이번 문제 본질과의 적합도·실패 양상을 별도 근거로 제시하고, 기존 환경의 실제 작동 여부도 검증 대상에 포함
- 구현 단계: "비슷하게 구현해줘" 를 받아도 레퍼런스 각 요소의 책임이 새 컨텍스트에서도 사는지 확인 후, 현재 시스템의 데이터 구조·의존성·사용 패턴에서 가장 단순한 형태를 도출. 제안을 "옵션 A vs B" 이분법으로 가두지 않기
- 문서 체계의 폴더 구성도 같다 — 형제 대상(다른 시스템)의 구성을 일관성 때문에 옮기지 않고 대상 성격에서 도출한다. 지킬 불변식은 지도를 따라 내려가 찾을 수 있는 구조(B-tree) 하나뿐
- **왜:** 기존 적용 ≠ 최적 선택 — 패턴은 원 시스템의 데이터 구조 산물이라 그대로 옮기면 같은 함정(silent degrade)·dead 요소만 남고, 옵션 고정은 그 너머의 적합한 형태를 놓친다

### 여러 파일 "동일 작업" 일괄 적용에도 각 파일 기존 정책 보존 (2026-06-02, 보강 1 · 최근 10-21)
- 각 대상 파일을 사전 Read, 명시된 핵심 변경만 적용하고 파일별 부가 정책(활성 범위·환경 분기) 차이는 보존. 의도 불명확하면 짧게 확인
- 보강(10-21): 형제 프로세서에 같은 보정 패턴을 옮길 때 원본에만 있던 전제(내부 레코드 필수 → 없으면 예외)를 따라 넣지 않는다 — 새로 추가하는 상태에만 가드를 걸고 기존 상태 분기의 동작은 그대로.
- **왜:** "동일 작업"의 의도 범위는 핵심 변경까지 — 부가 정책은 일부러 다르게 작성됐을 수 있다

### 사용자 작업 분담 명시 시 영역 침범 금지 (2026-06-12)
- "내가 ~할게" 분담 시그널이 있으면 그 영역은 미터치. 발견한 누락/이슈는 결과 보고에 한 줄 사실로만 남기고 수정은 위임
- **왜:** 분담은 책임 분리·의사결정 보존·사이드 이펙트 차단 목적

### 이전에 거부된 패턴과 표면 유사한 로직은 차이 선제 선언 후 도입 (2026-08-20)
- 거부 이력이 있는 패턴과 겉이 닮은 로직 도입 전 "거부하신 X 와는 이렇게 다름" 한 줄 선언 + 거부된 개념과 겹치지 않는 용어 선택
- 거부/롤백 지시엔 즉시 롤백 먼저, 사실 관계는 방어 없이 한두 줄로 갈라 답변
- **왜:** 구분 선언이 없으면 금지 위반으로 읽혀 신뢰 비용과 롤백/재도입 라운드트립이 실제로 발생한다

## 더 신경써야 할 것

### 기존 분기·동작 제거와 구현 전제 검증 — 유지가 기본값, 제거는 명시 지시 + 전 케이스 확인 후 (2026-09-23, 보강 5 · 최근 10-26, 병합 1 · 최근 10-27)
- **무엇:** 기존 분기·동작(폴백 경로, 구조 재편 요청에서 사용자가 열거하지 않은 동작 — 미수집 건 생성, 다른 경로와 중복으로 보이는 분기)은 유지가 기본값 — 제거는 명시 지시가 있을 때만, 애매하면 한 줄 확인 후 진행
- 제거 후보로 보이면 ①그 경로만 타는 데이터 케이스가 있는지 상류(코어) 코드로 전 상태·전 진입점(자동 흐름 + 어드민 수동 경로)을 열거해 확인 ②결론·근거·예외 케이스·외부 제약을 그 코드 위치에 TODO 로 남기고 제거는 이번 범위에서 하지 않고 별도 결정
- 유지/제거 판단은 텍스트 옵션 표(A 유지 / B 제거 + 각 영향)로 물으면 한 단어 답으로 끝난다
- 전제 검증(제거에 한정되지 않음): 사용자가 단정한 전제(데이터 관계·매칭 카디널리티 등)와 발언에 대한 내 해석은 구현 착수 전 코드/스키마/실측으로 검증 — 실제와 다르면 근거와 함께 보고하고 해석 분기(옵션)로 결정 위임. 전제가 반만 맞으면 맞는/아닌 쪽을 갈라 적는다
- 정보성 발언(외부 데이터 협의 결과)을 "이 분기는 불필요" 로 해석해 제거하지 않는다 — 그 분기만 타는 옛 구조 데이터가 실측에 보이면 덮고 진행하지 말고 보고한다(덮으면 기존 브랜드 수집이 깨진다). 해석 확인에 답이 없을 땐 "방향 확정 후 세부·미답 질문…" 항목의 기본값
- **왜:** 제거와 잘못된 전제 위 구현은 사이드 이펙트·통째 재작업 비용이 크다 — 결론을 코드에 남기면 다음 작업자가 같은 분석을 반복하지 않는다

### 미완성/컴파일 불가 편집은 문자가 아니라 의도를 구현 (2026-08-12, 보강 2 · 최근 11-02)
- 남은 참조·들여쓰기 잔재로 의도를 역추적해 동작하는 형태로 완성. 삭제하면 깨지는 구조적 필수 요소는 복원 + 구체적 실패 시나리오로 근거 명시 (조용한 복원 금지)
- 요청에 맞는/아닌 부분이 섞이면 갈라서 답변 — 맞는 쪽 즉시 적용, 아닌 쪽 근거 제시. 사용자 영역의 잔재는 보고만
- 사용자가 내 구현을 자기 스케치로 갈아끼우고 "컴파일 오류만 맞춰" 라고 하면 스케치가 설계다 — 구문만 고치고(컬렉션 리터럴·빠진 `throw`·중첩 `it`), 스케치가 걷어낸 내 가드는 복원하지 않고 뺀 항목을 보고 1줄로 남긴다. 형제 코드와 어긋나는 스케치의 선택(예외 타입)은 바꾸지 않고 참고 1줄만
- **왜:** 문자 그대로 완성하면 컴파일 불가 또는 필수 구조 소실로 조용히 깨지고, 전부 거절하면 맞는 지적이 유실된다

## 잘한 것 / 유지할 것

### 요청 범위 밖이라도 발견한 실질 버그·인프라 누락은 함께 보고 (2026-04-16, 보강 6 · 최근 11-05)
- **무엇:** 분석·구현 중 발견한 범위 밖 실질 문제(인코딩 버그, 신규 클라이언트가 실패 재처리 인프라(`ClientType` 등)에 미등록 등)는 결과 보고에 사실 1줄 + 영향("리스크·영향 서술" 형식: 원인→메커니즘→영향)으로 남긴다. 적용은 하지 않는다 — 사용자가 같은 티켓으로 끌어들이면 그때 작업. 한 줄짜리 수정이면 바로 편입되는 일이 잦다
- 버그·누락뿐 아니라 '더 맞는 소스' 발견도 같다 — 진행 중 흐름의 판정 소스로 더 맞아 보이는 API 를 발견하면 근거(주는 필드 vs 현 소스의 한계) 한 줄로 제안하고 적용은 지시 후
- 사용자가 실데이터로 가져온 결함이라도 현재 티켓 범위 밖(두 저장소·멱등 판정에 걸치는 키 변경 등)이면 같다 — 원인 확인·변경안 뒤의 질문은 '지금 수정 / 티켓만 생성' 두 선택지로. 티켓만이 선택되면 "노션·티켓 문서 작성 스타일" 의 후속 하위 티켓 규칙으로 즉시 생성
- 코드 검증으로 찾은 계약 불일치(요청이 거절돼 멈춤·같은 요청 재전송 등)는 결함인지부터가 판정이다 — 코드가 확정하는 것은 동작이고 의도는 모르므로 '티켓감' 으로 단정하거나 수정을 전제해 묻지 않고, 선택지를 '수정(지금/티켓) / 의도된 동작 또는 필요 조치를 단 예외로 기록' 으로 둔다. 보안 노출(인증 없이 열린 경로)도 같다 — 고치지 않고 보안이 필요하다는 표시를 단 예외로 확인한 사실 그대로 기록한다
- **왜:** 보고만으로 사용자가 범위 편입을 즉시 결정할 수 있고, 임의 적용은 범위 준수 룰과 충돌한다

### 리팩토링 범위 밖 개선은 별도 제안 / 필수 정합성 수정은 적용+명시 (2026-05-08, 보강 1 · 최근 06-18)
- 의미가 미묘하게 달라질 수 있는 개선(시간 비교·경계값 등)은 적용하지 않고 응답 끝에 "원하시면 적용" 1줄 제안
- 미적용 시 동작이 깨지는 필수 수정(전제가 깨뜨리는 호출부 등)은 적용 + "안 하면 X 깨짐" 명시. 기준: 의미 보존=제안 / 미적용 시 buggy=적용+명시. 작업 중 발견한 silent 버그도 함께 보고
- **왜:** 의미 변경이 리팩토링 커밋에 섞이면 리뷰/롤백 비용이 커진다

### 정보 범위를 좁힌 요청은 그 범위만, 보강 요청 시 추가 (2026-06-12, 보강 1 · 최근 11-03)
- "~에 대해서만", "간단히"면 최소 핵심만 작성. 같은 흐름의 보강 요청("X도 추가")엔 기존 유지 + 추가 (재작성 X)
- 보강(11-03): "목차처럼"·"llms.txt 처럼" 정리할 색인도 같다 — 날마다 쌓이는 기록의 색인에는 찾아가는 링크만 둔다(키 하나에 한 줄, 새 날짜는 그 줄에 링크만 덧붙임). 항목별 요약·키워드는 본문에 두고 색인에 되풀이하지 않으며, 찾는 축이 둘(서비스·도메인별 / 날짜별)이면 축마다 문서를 나눈다
- **왜:** 처음부터 풀로 채우면 사용자가 거꾸로 제거 요청을 해야 한다
