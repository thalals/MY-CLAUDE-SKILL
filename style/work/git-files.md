# git·파일 조작·자격증명

> 읽는 때: 커밋·브랜치·스테이징, 파일 덮어쓰기·삭제, 비밀값 파일을 다룰 때. 색인은 `index.md`.

## 하지 말아야 할 것

### 커밋·브랜치 조정 등 git 이력 변경·스테이징은 사용자가 직접 수행 — 진단·비파괴 시도는 직접 (2026-04-20, 보강 4 · 최근 11-05, 병합 1 · 최근 11-04)
- 구현 완료 시 변경 내역만 보고하고 커밋 여부도 묻지 않는다. 명시 요청 시에만 수행. 스테이징 정리(`restore --staged` 등)도 사용자 몫 — 인덱스와 작업 트리가 어긋나면 커밋될 내용과 실행할 명령만 보고한다
- 작업을 이어가려면 브랜치 조정(rebase·merge·switch·push)이 먼저 필요해도 직접 실행하지 않는다 — 읽기 전용 점검(log·merge-base·reflog, 수정분과 들어올 커밋의 파일 겹침)과 실패해도 상태가 안 바뀌는 시도(`--ff-only`)까지만 직접 하고, 명령 + 결과·리스크(force-push 필요 여부, 충돌 가능 파일) 표로 제시해 사용자가 실행하거나 "네가 실행해" 를 명시하게 한다. 실행했다는 알림이 오면 git log·대상 코드 존재를 재확인한 뒤 이어간다
- 상대 저장소(코어)에 짝 변경을 넣을 때는 사용자가 작업 중인 브랜치(다른 티켓이라도)의 워킹트리에 바로 넣고 새 브랜치·worktree 를 만들지 않는다 — 브랜치 분리는 사용자 결정이라 필요해 보이면 한 줄 질문. 검증용 throwaway worktree 는 별개
- 롤백/유실 재적용: `git status/log/stash list/reflog` 로 진단 → 유실분 vs 그 사이 유입된 변경 구분 → 같은 영역이 겹치면 먼저 알리고 통합 방향 확인 후 재적용
- 사용자가 머지·리베이스·충돌 해소를 마치고 "깨진 곳 고쳐 빌드 확인" 을 요청하면 컴파일 에러만 따라가지 않는다 — 머지 전에 내 변경분을 patch 로 떠 두고(`git diff HEAD -- <파일들>`, 신규 파일은 `--no-index /dev/null`) 머지 후 같은 명령의 patch 와 헤더를 뺀 채 diff 해, 충돌 해소에서 사라진 메서드·엉뚱한 곳에 들어간 블록·중복 import 를 복원하고 파일별 '문제 → 조치' 표와 빌드·테스트 결과로 보고한다. 참조까지 같이 유실되면 빌드로 안 드러난다
- **왜:** 커밋 구성·타이밍·메시지·브랜치 구조는 사용자가 관리한다 — 이력을 바꾸는 조작은 사용자 로컬·origin 상태를 바꾸고 되돌리는 비용이 크다

## 더 신경써야 할 것

### 파괴적 파일 조작 전 현재 상태 확인 — Write 덮어쓰기 / 동시 편집 / 롤백 재적용 (2026-06-26, 보강 2 · 최근 09-23)
- 덮어쓰기·롤백·동시 편집 전에 git/read 로 현재 상태(기존 파일 존재·동시 편집·유실분)를 먼저 확인한다. 덮으면 기존 내용(테스트 등)이 유실 → 발견 시 git 복구 후 병합. 내가 만들지 않은 코드는 덮기 전에 알린다
- **Write 덮어쓰기:** 신규로 착각해 Write 하지 않기 — 같은 경로에 파일이 있으면 Edit 로 전환하거나 기존 내용 보존
- **동시 편집:** 사용자가 같은 파일을 편집 중이면 매 수정 전 현재 내용 재확인, 내 설계와 다른 편집이 보이면 덮기 전에 두 방향의 차이·영향 범위부터 보고
- **왜:** 파괴적 조작 전 상태 확인을 건너뛰면 기존 코드/테스트나 그 사이 머지된 최신 작업이 조용히 유실된다 — git 복구는 되나 라운드트립 비용
