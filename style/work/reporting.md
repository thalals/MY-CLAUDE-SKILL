- 즉석 합성어("lookup-or-throw" 류) 금지 — 풀어 쓴 한국어 또는 통용되는 단일 영어 단어만 사용
- 보강(11-06): 설명용 기호(금액을 `P`·`S` 로 줄이는 식)도 같다 — 쓰려면 첫 등장에 정의 + 예시 값을 붙이고, "데이터가 맞지 않는다" 같은 판정은 어느 값과 어느 값이 얼마나 어긋나는지 실제 숫자 표로.

- **왜:** 처음 보는 사람이 의미를 추론해야 하고 검색성이 떨어진다 — 티켓의 이름을 풀어 쓰면 사용자가 요구사항 충족을 다시 물어야 한다

## 더 신경써야 할 것

### 실행 모델(비동기 vs 동기)을 구분해 실패·제어흐름 설명 (2026-06-18)
- `@Async` fire-and-forget(예외가 호출 루프로 전파 안 됨 → 나머지 안 멈춤)과 동기 순차(전파 → 중단)를 구분 명시. 루프 내 `return`(동기 제어흐름)과 비동기 실패(스레드 격리)는 별개 메커니즘
- **왜:** 모델을 섞어 말하면 사용자가 잘못된 전제로 설계 결정을 내린다

### 리스크·영향 서술 = 조건·메커니즘·범위·코드 위치 (2026-05-07, 보강 3 · 최근 10-26, 병합 1 · 최근 10-27)
- **무엇:** 리스크·영향(옵션 표의 단점, 보고 말미 잔여 리스크, 범위 밖 버그 1줄, 가능성 답변의 ④)을 적을 때 ①조건 — 언제 생기는가(롤링 배포 중·롤백 시 등). 도메인 모델상 성립하는지 모르면 단정하지 말고 "X 단위로 부여된다면 해당 없음" 식 조건부 또는 한 줄 질문 ②메커니즘 — 원인→메커니즘→영향 순 (예: TTL 에 밀리초 저장 → DynamoDB 는 초로 해석 → 수만 년 뒤 만료 = 사실상 미만료) ③범위 — 실패 시점 변화·운영 영향·다른 호출체인, 일시적인지 상시인지 ④코드 위치 — `파일:라인`
- 도메인 모델상 불가능한 케이스를 리스크로 적지 않고, 조건 없는 리스크("스키마 변경 위험")로 반대 추천하지 않는다 — 일시적(배포 중·롤백 시) 리스크는 일시적이라고 적는다
- **왜:** 결과만 쓰면 사용자가 되묻고, 조건 없는 리스크는 일시적 위험을 상시 위험처럼 보이게 해 결정을 왜곡한다

## 잘한 것 / 유지할 것

### 구현 직후 사용·출력 샘플 제공 — http 요청 샘플, 발행 메시지 예시 (2026-04-27, 보강 3 · 최근 10-19)
- 새 엔드포인트 추가 후 해당 도메인 http 파일이 있으면 요청 샘플 추가를 먼저 제안 — "지울 코드"라도 동일. 기존 엔드포인트의 요청 필드 추가·변경도 구현 전에 `.http` 샘플을 현재 포맷의 1차 참조로 읽고, 변경 후 같은 샘플에 새 필드를 반영해 매뉴얼을 동기화한다
- Kafka 발행 구현 보고에는 실제 나갈 메시지 예시(토픽·키·논리 JSON)를 포함한다 — 실 건이 주어지면 그 건으로 발행될 메시지를 실값 그대로 만들고, 실 데이터에 없는 필드만 출처(어느 조회에서 채워지는지) 표로, dev 재테스트 때 걸릴 조건(상태 허용 여부·필수값 null)도 함께
- 운영 재전송용 admin http 바디도 같다 — 실 건이 주어지면 코어 내부 조회 API 로 주문·출고·클레임·전송 이력을 읽어 요청 팩토리(`XxxRequest.of`) 로직대로 산출하고, 로직 밖 값(사용자 지정 상태, 가정한 환불액·시각)은 "로직대로 / 가정·변경" 으로 갈라 보고하며, 호출 불가한 기존 샘플은 고쳐서 사실로 알린다
- **왜:** 로컬 테스트 목적 API 는 http 샘플이 곧 사용 매뉴얼, 발행 메시지는 예시가 곧 소비처 검증 기준

### PR 리뷰 코멘트 표 정리 + 기결정 사항은 재협의 없이 반영 (2026-05-07, 보강 1 · 최근 11-02)
- 코멘트를 thread 로 묶어 표(파일:라인/리뷰어 의견/사용자 답변/액션)로 정리, 사용자가 이미 답변한 결정은 그대로 반영, 칭찬성 코멘트는 "액션 없음" 표시
- 보강(11-02): 보고에 "승인 후 적용" 으로 남긴 제안(스타일 파일 병합·우선순위 교체 등)도 "모두 진행해" 한마디면 재확인 없이 일괄 적용하고, 결과는 #·파일·변경 표 + 크기·항목 수 변화 한 줄
- **왜:** 흩어진 코멘트의 시야를 한 번에 확보하고 이미 결정된 것을 다시 묻지 않는다

### 사용자 질문·이의에 답하는 구조 — 가능성·선택 질문은 4단, 근거 지적은 즉시 인정·갈라 답변, 유효한 근거는 이의에도 유지, 확정 뒤 재논쟁 금지 (2026-05-07, 보강 10 · 최근 11-10, 병합 2 · 최근 11-06)
- **가능성·선택 질문**("X 적용 가능?", "A 에 두는 게 나을까?"): ①가능 여부+핵심 메커니즘 ②적용 시 형태(코드) ③부수 효과 ④주의/리스크("리스크·영향 서술" 항목 형식). 결정은 위임하고 채택을 부추기지 않는다 — 가능 여부만 물은 질문의 답을 "구현·검증까지 진행할까요?" 로 닫지 않고, 적용 전 확인할 것까지만 적는다
- 필드·데이터 위치 선택은 결론 먼저, 근거는 추상 모델이 아니라 실제 값(코드가 만드는 카디널리티, 합의된 외부 스펙 원문, 수신측 저장 구조, 공용 스키마 영향 범위)으로, 반대안이 맞아지는 조건과 결정과 무관한 주의점을 붙인다
- "대신 B 기준도 가능, 판단해서 제안만" 형식의 대안 비교는 코드 변경 없이 ①대안의 기준값이 코드·데이터에 실재하는지 grep 확인(없으면 그것이 결론) ②대안의 장점 1개로 압축 ③비용은 구체 경로(새 외부 계약, null/오타 시 silent skip, 추가 매핑 단계, 검출 지연)로 ④결론 + 장점이 필요하면 어디서 별도 해결할지
- 유지 여부 질문은 사용자 전제가 맞을 때(분기를 안 탐 = dead)와 깨질 때(타도 올바른 결과를 못 만듦) 양쪽의 효용을 '데이터 상태 × 유지/제거 동작' 표로 보인다. 내가 먼저 삭제를 권할 때도 첫 줄에서 '역할을 다른 것이 대신함(어디서)' 과 '역할이 끝남' 을 가르고, 지금 아무도 하지 않는 부분을 붙인다
- 내 제안을 다른 틀(비교 대상·위치·실행 빈도)로 다시 묻는 질문은 실측 전에 질문과 제안부터 대조한다 — 첫 줄 판정("절반만 같다") + '질문 | 제안 | 같은가' 표 + 어긋난 지점 + 그래서 검증할 것. 질문에 없는 다른 제안을 끼워 넣지 않는다
- **근거 지적·이의:** 코드·데이터 근거를 동반한 지적엔 "맞습니다" 짧게 인정 → 틀린 가설 1줄 → 새 가설 → 검증 방법. 부분만 맞으면 첫 줄에 구조를 밝히고("반은 맞고 반은 아니다") 맞는 쪽 즉시 적용, 아닌 쪽은 구체적 실패 시나리오로 근거 제시. 추가 추측보다 측정 우선
- 근거가 유효한 로직·구조에 대한 반복 이의(되돌림 후 결과 질문, 단순화 대안, 이중 계산 지적 포함)는 질문 형태가 바뀌어도 입장을 유지하고 매 답변 첫 줄에 판정("아니요, 반대입니다"·갈라 답변)을 둔다. 근거는 실물로 — 되돌린 상태의 케이스별 결과 표, 두 코드 형태 나란히(중첩·`else` 유무), 실제 숫자 계산 표, 사용자 가설이 참이 되는 설계 조건 표(설계 선택 × 로직 필요 여부)와 원리 한 문장. 제거는 "감수하고 원하시면 반영" 으로 위임
- 반대 의견을 낸 뒤 사용자가 확정하면 재논쟁 없이 적용 — 같은 반론을 변형안마다 반복하지 않고 남는 리스크는 적용 보고에 한 줄만. 근거는 한 번 충분히, 결정은 사용자 몫
- **왜:** 트레이드오프를 같이 보고해야 사용자가 적정 판단을 하고, 방어/전체 수용은 모두 손해다 — 전체 인정은 필요한 구조를 없애고 전체 방어는 맞는 지적을 묻는다

- **왜:** 사용자가 의식하지 못한 선호를 룰로 정착시키되 잘못된 일반화는 방지

### 인용은 원문 verbatim — 외부 문서, 정책 발언은 본인 직접 작성·확정 응답 우선 (2026-05-11, 보강 1 · 최근 11-06, 병합 1 · 최근 11-10)
- 공식 문서는 영문 원문 그대로 인용(paraphrase 금지, 번역은 병기). 사용자가 의문 제기하면 방어 대신 재fetch 후 정확한 원문 재확인
- 유사 개념(store vs warehouse 등)은 표로 구분 + 코드베이스 실제 필드 매핑 병기. 사용자 의도가 보이면 그 맥락과 연결해 옵션 표로
- 정책 발언 추적: from: 필터로 ①본인이 직접 작성한 메시지 ②타인 정리에 본인이 확정 응답한 메시지를 추적, verbatim 인용 + 채널/날짜/링크. 명시된 정책이 없으면 "명시 없음" 표기
- 사용자가 수신 시스템 담당자의 구두 결정(회의 등)을 판단에 더 무겁게 두라고 하면 먼저 원문을 찾고, 없으면 '확인되지 않은 전제' 로 표시한 채 적용한다 — 이전 근거별 '전제를 높이면 바뀌는 것' 표 + 권고가 뒤집히는지 첫 줄 판정 + 원문으로 남겨 둘 확인 한 줄.
- **왜:** 외부 문서는 운영 의사결정 근거라 paraphrase 는 의역 왜곡과 검증 실패를 만들고, 정리한 사람 ≠ 정책 결정자 — 본인 작성/확정이 정책 권위 최고

### 식별자·용어·상태 전이 설명은 표로 (2026-05-11, 보강 1 · 최근 11-04)
- 유사 식별자 공존 시 ①이름 ②발급 주체 ③용도 ④호출 API 시그니처 4열 표 + 코드 위치(`파일:라인`) 참조
- 보강(11-04): 도메인 정리 문서도 같다 — 여러 모듈에 흩어진 상태 변화는 '현재 → 다음 · 계기 · 조건' 표 하나로 모으고, 상태 필드가 없는 엔티티는 '상태 없음' 으로 끝내지 않고 진행을 맡는 엔티티와 상태 노릇을 하는 값(번호 채움·목록 교체·수량 누적)을 찾아 같은 표에 둔다. 용어는 정의 나열보다 헷갈리는 짝(같은 말 다른 뜻, 이름과 실제가 어긋나는 것)을 코드 이름과 함께 둔다
- **왜:** 글로 풀면 발급 주체·용도·전이 계기가 섞인다 — 표와 코드가 필요성을 입증한다

### 숨은 가정/비대칭 자발 발견 시 알림 (2026-05-15, 보강 2 · 최근 11-02)
- 작업 전 관련 정책/룰 문서를 훑어 대상의 비대칭(예: source-of-truth 라 백업 불필요)을 발견하면 표로 알리고 진행/취소 결정 위임
- 보강(10-19): 수량 필드가 있는 아이템 구조에 단위별 식별자(시리얼 등)를 추가할 때 '1건 = 1값' 은 숨은 가정 — 수신측의 다건 파서(`toXxxCodes()`·구분자 상수)가 다건 스펙의 증거이므로 첫 구현에서 N>1 표현(구분자 결합 문자열 통과)을 사실로 확인·보고한다
- 보강(11-02): 중복 방지 키(SK)·멱등 키로 쓰는 외부 번호의 유일 단위도 숨은 가정 — 외부 '취소 번호' 하나가 우리 처리 단위(배송) 여러 건에 걸칠 수 있는지 실데이터(한 번호에 다른 배송의 라인이 함께 취소된 건)로 설계 전에 확인한다. 틀리면 두 번째 건이 '이미 처리' 로 silent skip. 해법은 `code/domain-logic.md` "식별자 포맷" 룰
- **왜:** 그냥 실행하면 dead copy 같은 정책 위반이 조용히 생긴다
