# 스킬 작성·개선

> 읽는 때: 스킬(SKILL.md)을 새로 만들거나 고치거나 이름을 바꿀 때. 색인은 `index.md`.

## 더 신경써야 할 것

### 스킬 형식·위치·완료 단계 — 이 파일 하나로 시작해 끝까지 간다 (2026-11-18)
- 이름(`name`): 동사 먼저, 영문 소문자·하이픈 (아래 "신규 스킬/룰 작성·개선" 항목)
- `description`: 무엇을 하는지 + 언제 쓰는지를 한두 문장(`Use when …`)으로. 사용자가 실제로 쓰는 호출 문구 나열은 `when_to_use` 에 둔다 — 트리거의 단일 소스가 한 필드여야 고칠 때 한 곳만 본다. 인자를 받으면 `argument-hint`
- 본문: `# 제목` + 한 줄 요약 → `## 사용법` → `## 실행 절차`(`### n단계: …`) → `## 규칙`. 한국어로 쓰고, 절차 안의 판단 기준은 표로
- 위치: 여러 저장소에서 쓰면 `~/.claude/skills/<name>/`, 한 저장소 전용이면 그 저장소의 `.claude/skills/<name>/`
- 완료 단계(만들거나 고친 뒤 매번): iCloud 백업 → 개인 스킬 저장소 `README.md` 의 스킬 절·구성 표 갱신 → sync 스크립트. 경로·명령은 전역 `CLAUDE.md` 'iCloud 백업 규칙' 이 단일 소스다. 긴 세션에서는 그 사이 `CLAUDE.md` 가 바뀌었을 수 있으니(세션 시작 때만 읽힌다) 완료 단계 직전에 그 절을 다시 읽는다
- 스킬 작성 방식은 이 파일이 plugin 의 스킬 작성 스킬(압박 테스트·eval 을 요구하는 것)보다 우선한다 — 검증은 본인 케이스 dogfood 로 하고, 압박 테스트·eval 은 사용자가 요청할 때만
- 이름 바꾸기·삭제는 스킬 폴더, iCloud 백업 폴더, README 를 같은 편집에서 함께 맞춘다
- **왜:** 형식·완료 단계가 여러 문서(색인 행, 문서 규칙 파일, 전역 지침, 기존 스킬 예시)에 흩어져 있으면 단계가 빠진다 — 2026-11-18 에 스킬을 새로 만들면서 세션 도중 추가된 README 갱신 단계를 놓쳤다

## 잘한 것 / 유지할 것

### 신규 스킬/룰 작성·개선 — 개선은 잰 원인에서 출발, 직후 본인 절차로 dogfood 검증, 딸린 도구는 읽는 대상 옆 + 지도·스킬에 등재 (2026-05-15, 보강 6 · 최근 11-18)
- 스킬 개선 요청은 쌓인 산출물을 사용자가 그것으로 확인하려는 목적에 비춰 고친다 — 목적에 의미 없는 요소는 빼고, 유지하라고 한 부분은 그대로 두며, 산출물을 길게 만들지 않는다. 지시받은 수정과 함께 그 실행에서 잰 값을 근거로 추가 개선안을 낸다 (11-18)
- 만든 절차를 본인 케이스에 즉시 적용해 빠진 단계·모호한 표현을 발견. 자기 적용이 불가한 룰은 다음 실제 작업에서 시연
- 대화에서 좋았던 산출물 형식을 스킬로 만들 때는 템플릿만 옮기지 않고 그 형식이 좋았던 이유(실제 diff 기반, 실측·추론 구분 등)를 작성 규칙으로 넣고, 완료 보고에 방금 작업에 스킬을 적용한 출력 + 빠진 단계 유무 한 줄을 붙인다. 반복한 대화 절차를 스킬로 만들 때는 그 대화에서 사용자가 정정한 것(틀린 출처 대체, 정정은 같은 산출물 수정 등)도 규칙으로 넣는다. 스킬 이름은 기존 스킬처럼 동사 먼저(`collect-…`, `record-…`, `create-…`) 영문 소문자·하이픈으로, 한글 이름 요청도 같은 순서로 옮긴다 (11-18)
- 스킬·기록에 딸린 도구(스크립트)는 작업 저장소가 아니라 그 도구가 읽는 것 옆에 둔다 — 기록 문서·규칙을 읽으면 규칙 파일 옆, 세션 기록을 읽으면 스킬 폴더(백업 규칙 대상). 만들거나 고치면 같은 편집에서 에이전트가 처음 읽는 지도·스킬에 용도·실행 시점을 한 줄 적는다. 도구로 옮길 것은 값 계산(시각 추출·커밋 대조·목록 대조)이고, 어느 문서가 자리인지 같은 의미 판단은 지도를 읽어 LLM 이 한다
- 스킬·기록 체계 개선(비용·정확도)은 짐작이 아니라 세션 원본에서 잰 원인에서 출발한다(예: 비용은 읽는 파일 크기보다 '호출 수 × 그 시점 맥락 크기' 가 정한다) — 공식 문서 원문으로 근거를 달고, 개선 요청이어도 잰 이득이 작은 변경은 수치(고칠 링크 수 대비 줄어드는 크기)를 대고 하지 않으며, 아직 못 잰 효과는 '어림' 으로 적고 다음 실제 실행에서 다시 잴 값을 남긴다 (11-16). 개선안은 이번 실행에서 잰 값과 함께 번호 목록으로 내면 사용자가 번호로 골라 바로 진행된다 (11-18)
- 스킬에 판단 예시를 더할 때 기존 지시(정의 문장 포함)와 반대되는 예시만 넣지 않는다 — 반대 문구를 grep 해 함께 고치고 예시는 판단 보조로 둔다. 규칙·예시가 서로 다르게 말하면 모델은 지시 문장을 따르거나 매번 다르게 판단한다. 스킬 개선은 다음 실행부터 적용이 기본이라 지난 산출물 재작성은 제안하지 않는다 (11-18)
- **왜:** self-application 가능 여부가 룰 명확성의 기준 — 등재하지 않은 도구는 다음 에이전트가 모른다. 짐작한 원인을 고친 개선은 효과도, 효과를 다시 잴 길도 없다
