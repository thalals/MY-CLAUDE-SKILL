# Collect Feedback

대화 중 사용자가 준 피드백을 수집하여 스타일 파일에 반영한다.

## 호출 시점

트리거 조건은 frontmatter `when_to_use` 참조.

**트리거 누락 안티패턴 (실제 발생, 반복 금지):** "잘했어" → 단순 응답으로만 처리 → 사용자가 "칭찬을 했는데 피드백 수집할게 없나보네 ?" 로 두 번 알려야 실행. 칭찬 메시지를 받으면 응답 텍스트를 쓰기 전에 먼저 이 스킬을 호출하고, 결과 보고에 칭찬 응답을 통합한다.

## 수집 대상

대화 전체를 스캔하여 아래 항목을 찾는다:

| 유형 | 시그널 | 예시 |
|------|--------|------|
| 금지 | "~하지 마", "~안 해도 돼", "왜 ~했어?" | "테스트에 주석 달지 마" |
| 수정 요청 | 네이밍 변경, 구조 변경, 제거 요청 | "이름을 startDate로 바꿔" |
| 작업 방식 | "~이렇게 해줘", "~가 더 나을 것 같아" | "PR은 하나로 묶어줘" |
| 스타일 선호 | 설계/코드 패턴 선호 표현 | "enum은 companion object에 fromName 넣어" |
| 칭찬/긍정 | "좋아", "맞아", "잘했어", "최고", "굳", "오 괜찮다", 수정 없이 수락 | 왜 칭찬했는지 분석하여 기록. 분석 대상이 명확하지 않으면 직전 작업의 결정/접근/결과물에서 비결준점을 찾아 룰화 |

## 실행 절차

1. **대화 스캔** — 위 수집 대상에 해당하는 발언을 모두 찾는다
2. **분류** — 각 항목을 아래 기준으로 분류:
   - 코드 작성/구조/패턴/단위테스트 코드 관련 → `code_style.md`
   - QA 테스트 시나리오 작성/검증 프로세스/체크박스 사용/실 데이터 기반 검증 관련 → `test_work_style.md`
   - 업무 프로세스/커뮤니케이션/설계 방식/일반 문서 스타일 관련 → `feedback_work_style.md`
3. **현재 파일 읽기 + 크기 측정** — 대상 파일을 읽고 `wc -l` 로 줄 수를 확인한다 (아래 "파일 크기 관리" 참조)
4. **기존 항목 검색** — 신규 항목을 쓰기 전에 실행한다:
   ```bash
   grep -n "<핵심키워드>" <대상파일>
   ```
   피드백의 핵심 키워드(예: `nullable`, `네이밍`, `DTO`, `테스트`, `노션`)로 검색하여 같은 주제를 다루는 기존 항목이 있는지 확인한다. 이 검색 결과를 5번 판단의 근거로 쓴다.
5. **반영 방식 결정** — 4번 결과에 따라 셋 중 하나를 고른다:

   | 상황 | 방식 |
   |------|------|
   | 같은 규칙을 이미 다룬 항목이 있음 | **보강** — 기존 항목에 새 사례를 하위 불릿으로 추가, 날짜 갱신 |
   | 같은 주제를 다루는 항목이 2개 이상 흩어져 있음 | **병합 제안** — 상위 개념 제목 하나로 통합, 각 사례는 하위 불릿으로 보존. 실제 적용은 사용자 승인 후 |
   | 관련 항목이 없음 | **신규** — 아래 항목 작성 규격에 맞춰 해당 섹션에 추가 |

   수집할 피드백이 없으면 "수집할 피드백이 없습니다" 로 종료한다.
6. **파일 수정** — Edit 도구로 업데이트
7. **결과 보고** — 아래 "결과 보고 형식" 준수

## 항목 작성 규격

각 항목은 다음 구성만 포함한다:

```markdown
### <규칙을 한 줄로 (YYYY-MM-DD)>

- **무엇:** 지켜야 할 동작 1~2줄
- **왜:** 근거 1줄
- (필요시) 코드 예시 3줄 이하
```

- **본문 8줄 이하.** 넘으면 규칙이 두 개 이상 섞여 있다는 신호 — 분리하거나 상위 개념으로 압축한다
- 세션 고유 맥락(티켓 번호, 특정 파일 경로, 대화 재현)은 넣지 않는다 — 다음 세션에서 self-contained 하게 읽혀야 한다
- 장문 배경 서술 대신 결론을 쓴다

## 파일 크기 관리

3번 단계에서 측정한 줄 수에 따라 동작이 달라진다:

| 줄 수 | 동작 |
|-------|------|
| ~400줄 | 정상. 그대로 추가 |
| 400~600줄 | 신규 추가 전 4번 검색 범위를 넓혀 병합 가능 항목을 우선 찾는다 |
| 600줄 초과 | 결과 보고에 **분할 제안 1줄**을 포함한다 (어느 섹션을 어느 파일로 분리할지). 실제 분할은 사용자 승인 후 |

스타일 파일은 매 세션 컨텍스트에 로드되므로, 줄 수 증가는 모든 작업의 비용이다. 같은 규칙을 두 곳에 쓰는 것이 가장 비싼 실수다.

## 결과 보고 형식

사용자가 판단할 수 있도록 아래를 모두 포함한다:

- **각 파일별 표** — 변경이 있는 파일마다 `| 섹션 | 항목 | 시그널 | 방식 |` 표로 정리 (추가 항목 + 사용자 원문 시그널 + 보강/병합/신규 구분)
- **파일 크기 1줄** — 변경한 파일마다 `변경 전 → 변경 후` 줄 수. 600줄 초과 시 분할 제안 포함
- **추가 없는 파일도 한 줄 표시** — "변경 없음" 만 쓰지 말고 사유 1줄 (예: "이번 대화의 코드 룰들은 작업 판단 기준 성격이라 `feedback_work_style.md` 로 분류")
- **헷갈릴 수 있는 분류는 근거 명시** — 같은 항목이 다른 파일에 들어갈 가능성이 있으면 왜 그 파일을 선택했는지 1줄 사유. 사용자가 분류 적정성을 즉시 판단 가능해야 함

## 실행 컨텍스트 제약

이 스킬은 `context: fork` 로 서브에이전트에서 실행된다. 부모 대화 이력은 전부 상속되므로 대화 스캔은 정상 동작하지만, **메인 세션으로 돌아가는 것은 마지막 assistant 메시지 하나뿐이다.**

- **결과 보고 전체를 마지막 메시지 하나에 담는다.** 표를 여러 턴에 나눠 출력하면 앞부분이 유실된다
- 중간 진행 상황을 사용자에게 알리려 하지 않는다 — 어차피 전달되지 않는다
- 사용자에게 확인이 필요한 사항(병합·분할 제안)은 마지막 메시지 안에 **질문 형태로 남긴다**. fork 안에서 사용자에게 직접 물을 수 없다

## 규칙

- **정보를 삭제하지 않는다.** 병합은 중복 서술만 제거하고 각 사례는 하위 불릿으로 보존하는 것을 뜻한다 — 규칙 자체를 없애는 것이 아니다
- **병합·분할은 사용자 승인 후 적용한다.** 보고에 제안만 남기고 임의로 재구성하지 않는다
- 파일을 새로 만들지 않는다 (분할 승인 시에만 예외)
- 칭찬은 "잘한 것 / 유지할 것" 섹션에 **왜 칭찬했는지 분석**하여 기록한다
