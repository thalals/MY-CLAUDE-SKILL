# research-efficiency

대화가 참고하는 지시와 반복 절차의 효율을 이어서 연구하는 순서다. 효율은 품질(지시가 지켜지고 기록이 맞는 것)을 지키면서 드는 토큰과 값을 줄이는 것이다. 연구는 한 번에 끝나지 않는다. 매번 지난 연구가 남긴 장부에서 시작해, 재고, 견주고, 다음 시도를 정하고, 장부를 고쳐 놓고 끝낸다.

이 스킬은 대화 내용이 필요 없고 장부에서 시작한다. 새 세션에서 부른다. 무거운 대화에서 부르면 연구 자체가 비싸진다(findings F-03).

## 연구 대상

- 늘 실리는 맥락: 세션 첫 호출에 실리는 것. CLAUDE.md, 메모리 색인, 스킬 목록, 훅이 넣는 글, 커넥터 안내, 도구 정의. 모든 호출이 다시 읽는다.
- 필요할 때 읽는 지시: 스타일 색인과 주제 파일, 스킬 본문과 reference, 볼트 규칙 파일과 지도. 읽은 뒤의 모든 호출이 다시 읽는다.
- 반복 절차: record-obsidian, collect-feedback, collect-worklog, jira 같은 스킬의 한 번 실행.
- 효과: 지시가 실제로 지켜졌는가. 실행 뒤 사용자가 고쳐 달라고 한 횟수, 같은 피드백이 다시 나온 횟수, lint 결과, 평가 시나리오.

## 연구 장부

`<스킬>/research/` 에 있다. `<스킬>` 은 이 스킬을 부를 때 알려 주는 Base directory 다.

- `state.md`: 현황. 지금 어디가 큰지, 무엇을 기다리는지, 다음에 할 일. 연구할 때마다 지금 상태로 고쳐 쓴다.
- `findings.md`: 재서 확인한 사실. 근거 명령과 한계를 함께 적는다. 틀린 것으로 드러나면 지우지 않고 정정 줄을 더한다.
- `directions.md`: 개선 방향. 방향마다 근거, 방법, 예상, 틀렸다고 볼 기준, 상태를 적는다.
- `attempts.md`: 시도. 무엇을 바꿨는지, 사전 측정, 예측, 사후 측정, 품질 확인, 결론을 적는다.
- `runs.tsv`, `base.tsv`: 도구가 적는 측정값. 손으로 고치지 않는다.

장부 항목의 형식은 각 파일 머리말에 있다. 번호(F-, D-, A-)는 한 번 붙이면 바꾸지 않는다.

## 도구

`python3 -B "<스킬>/scripts/efficiency.py" <명령>` 으로 돌린다. 숫자는 이 도구 출력에서 나온 값만 쓰고, 곱하거나 나눈 값은 식을 함께 적는다. 세션 ID 와 서브에이전트 ID 는 `runs` 출력에 앞 8자로 나온다.

- `status`: 연구를 시작할 때 한 번. 현황, 방향과 시도의 상태, 아직 안 잰 실행과 진행 중으로 적힌 줄을 낸다.
- `runs --days 30 --save`: 스킬 실행을 재서 runs.tsv 에 적는다. 다시 잰 줄은 새 값으로 바뀐다. `runs --session ID --skill 이름` 은 한 세션의 실행을 자세히 낸다.
- `stats --skill 이름 --since 날짜 --until 날짜`: runs.tsv 의 구간별 중앙값. 바꾸기 전후를 견줄 때 쓴다. `--model`, `--ctx-below`, `--ctx-above` 로 모델과 시작 맥락이 비슷한 실행만 고른다.
- `carry --session ID --skill 이름` (서브에이전트는 `--agent ID`): 한 실행에서 맥락에 들어온 것과 그것을 다시 읽은 값. 어디를 줄일지 찾을 때 쓴다.
- `after --session ID --skill 이름`: 실행 뒤의 사용자 발언. 정정 요청이 몇 번이었는지 세는 품질 확인에 쓴다.
- `base --project 이름일부 --save`: 새 세션 첫 호출의 크기와 구성. 늘 실리는 맥락을 바꾼 뒤에 쓴다. `base --list` 는 세션별 추이다.
- `reads --days N`: 지시 파일을 참조한 횟수와 스킬 호출 횟수.
- `total --session ID`: 세션 전체에서 본 대화와 서브에이전트가 쓴 것.
- `check --session ID`: 하니스 자체 집계와 이 도구 합계의 차이. 도구를 고친 뒤와 수치가 의심스러울 때 쓴다.

지표 정의, 실행 구간을 자르는 법, 품질 신호, 알려진 함정은 `<스킬>/reference/metrics.md` 에 있다. 수치를 해석하거나 장부에 사실을 쓰기 전에 읽는다.

## 한 번의 연구

1. `status` 를 돌린다. 사용자가 대상이나 질문을 줬으면 그것부터, 없으면 state.md 의 '다음에 할 일' 부터 한다.
2. 잰다. `runs --days 30 --save` 로 아직 안 잰 실행을 적고 진행 중으로 적힌 줄을 다시 잰다. 직전 연구 실행의 비용도 이때 잡힌다. 늘 실리는 맥락이 바뀌었을 만하면(플러그인, 커넥터, CLAUDE.md, 스킬 설명 변경) `base --project 이름일부 --save` 를 한다. `status` 의 요약에는 진행 중인 실행이 섞일 수 있으므로, 장부와 판정에는 다시 잰 뒤의 `stats` 값을 쓴다.
3. 측정 대기인 시도를 판정한다. attempts.md 의 '틀렸다고 볼 기준' 을 `stats` 의 전후 값과 견준다. 모델이 다른 실행끼리는 정가 환산이 아니라 기준 단가 환산과 누적 입력으로 견주고, 시작 맥락이 비슷한 실행은 `--ctx-below`, `--ctx-above` 로 따로 본다. 필요한 횟수와 합격 폭은 그 시도의 기준 줄에 미리 적힌 대로 한다. 품질 확인 줄은 `after` 로 채운다. 횟수가 모자라거나 품질 확인 값이 비어 있으면 결론은 더 재기다. 결론은 채택, 되돌림, 더 재기 가운데 하나이고, 되돌림이면 직접 되돌리지 않고 5단계에서 사용자가 정할 것으로 올린다. 판정한 시도와 그 방향의 상태를 같은 편집에서 고치고, 확인된 것은 findings.md 로 옮긴다.
4. 새 방향을 찾는다. 큰 항목부터 본다. 스킬은 `stats` 의 합과 한 번 중앙값 둘 다로, 실행 안은 `carry` 의 큰 단계로, 늘 실리는 맥락은 `base` 의 큰 구성 요소로 본다. 방향이 하나도 없는 큰 스킬에는 '먼저 잰다' 방향을 올린다. '먼저 잰다' 방향은 재서 예상과 기준을 채운 뒤 후보로 올리고, 잰 이득이 작으면 수치를 대고 기각한다. 예상은 토큰과 기준 단가 환산 둘 다로 적는다. 바꾸는 방법이 Claude Code 기능에 달려 있으면 공식 문서 원문으로 확인한다.
5. 다음 시도를 사용자와 정한다. 방향 가운데 추천 순서와 이유(예상 이득, 품질 위험, 드는 것)를 보고하고 고르게 한다. 지시, 스킬, 설정, 규칙 파일은 사용자가 고른 뒤에만 바꾼다.
6. 시도를 적용한다. 바꾸기 전에 attempts.md 에 사전 측정, 예측, 틀렸다고 볼 기준(필요한 횟수와 합격 폭), 품질 확인 방법을 먼저 적는다. 사후 측정은 그 뒤 실제 사용이 쌓인 다음 연구에서 한다. 같은 때에 다른 것도 바뀌면 그 사실을 적는다. 습관을 바꾸는 시도는 시작한 날을 적는다.
7. 마친다. state.md 를 지금 상태로 고쳐 쓰고, 스킬 폴더를 iCloud `claude/skills/research-efficiency/` 에 복사하고 `bash "$HOME/Desktop/hmin/MY-CLAUDE-SKILL/.sync/sync.sh"` 로 동기화한 뒤 보고한다.

한 번에 1~7을 다 하지 않아도 된다. 재기만 하는 날은 1, 2, 7이고, 사용자가 방향을 고른 날은 6, 7이다.

## 바꾸는 길

- 스타일 규칙은 collect-feedback 으로만 고친다.
- 볼트 구조와 규칙, record-obsidian 은 사용자가 5단계에서 고른 것만 고친다. 그 대화에서 정하지 못한 채 끝나면 볼트 `proposals.md` 에 제안으로 남겨 다음 기록 보고가 다시 묻게 한다.
- 그 밖의 스킬, CLAUDE.md, 설정(플러그인, 커넥터, 훅)은 5단계에서 사용자가 고른 것만 고친다.
- 이 스킬과 도구를 고치면 metrics.md 와 위 도구 목록을 같은 편집에서 맞추고 `check` 로 도구 합계를 다시 대조한다.

## 지키는 것

- 같은 도구, 같은 정의로 잰 값끼리만 견준다. 예전 보고의 숫자는 도구로 다시 내서 쓴다.
- 한두 번 잰 값으로 줄었다고 쓰지 않는다. 횟수와 조건을 함께 적는다.
- 비용이 줄어도 품질 확인이 없으면 채택하지 않는다.
- 틀린 사실과 실패한 시도를 지우지 않는다. 다음 연구가 같은 길을 다시 가지 않게 하는 기록이다.
- 연구 자체의 비용도 잰다. 이 스킬의 실행은 다음 연구의 2단계에서 runs 에 잡힌다. 서브에이전트를 쓰면 `total` 이나 `carry --agent` 로 잰 누적 입력을 보고에 적는다.
- 장부에는 숫자와 식별자만 옮긴다. 도구 출력에 섞인 명령 설명, 대화 내용, 비밀값은 옮기지 않는다.
- 장부에 자리가 없는 내용은 새 파일을 만들지 않고 보고에서 구조 제안으로 올린다.
- 세션 원본은 읽기만 한다.
