# 개선 방향

> 아직 확인하지 않은 가설과 할 수 있는 개선을 둔다. 한 방향은 `## D-번호 제목` 하나이고 대상, 근거(findings 번호와 값), 방법, 예상(토큰과 기준 단가 환산), 틀렸다고 볼 기준, 상태를 적는다. 품질 위험과 드는 것은 있을 때 적는다. 측정을 넓히는 방향은 예상 대신 '끝났다고 볼 기준' 을 적는다. 상태는 먼저 잰다(예상을 아직 댈 수 없음), 후보, 시도 중(attempts 번호), 채택, 기각 가운데 하나와 날짜다. 채택하거나 기각해도 지우지 않는다.

## D-01 기록을 무거운 대화가 아니라 가벼운 맥락에서, 캐시가 식기 전에 돌린다
- 대상: record-obsidian 을 어느 세션에서 언제 부르는가
- 근거: F-03(시작 맥락을 다시 읽은 값이 두 실행에서 누적 입력의 66%, 92%이고 값으로는 26%, 46%), F-04(옛 구조 16번 가운데 6번이 식은 캐시에서 시작했고 그 첫 호출이 실행 값의 20~41%)
- 방법: (가) 작업을 마친 직후, 캐시가 살아 있을 때 기록한다. (나) 새 세션에서 record-obsidian 의 `start.py --session <ID>` 로 지난 세션을 기록한다. (다) 한 세션을 몇 주씩 이어 쓰지 않는다. 습관을 바꾸는 방향이라 시도로 올릴 때는 시작한 날을 적고, 지켜졌는지는 실행마다의 시작 맥락과 첫 호출 캐시 쓰기로 본다.
- 예상: 새 구조의 본 대화 호출은 첫 실행에서 16번이었다(A-01). 시작 맥락이 옛 중앙값 322,715 면 본 대화가 시작 맥락을 다시 읽는 값이 322,715 × 16 = 약 516만 토큰($1.03)이고, 8만이면 128만($0.26)이다. 식은 캐시를 다시 쓰는 값은 322,715 × $8/백만 = $2.58 이고 8만이면 $0.64 다.
- 틀렸다고 볼 기준: 시작 맥락 10만 아래에서 돌린 새 구조 기록 3번의 본 대화 누적 입력 중앙값이 300만 이상이면 틀린 것이다. `stats --skill record-obsidian --since "2026-11-16 17:00" --ctx-below 100000` 의 '본 대화 누적 입력' 으로 본다.
- 품질 위험: (나) 는 대화 내용을 원본 타임라인으로만 본다. 대화에서 정한 이유와 결정이 빠질 수 있다. 사후 정정 요청 수로 본다.
- 드는 것: (가)(다) 는 부르는 습관만 바꾼다. (나) 는 지금 스킬로 된다.
- 상태: 후보 (2026-11-17)

## D-02 record 서브에이전트의 생각 토큰과 모델
- 대상: record-obsidian 4단계가 띄우는 서브에이전트
- 근거: F-02(출력 단가는 캐시 읽기의 100배), A-01 첫 실행의 서브에이전트 출력 174,833 중 생각 117,810
- 방법: 서브에이전트를 낮은 effort 로 부르거나 Sonnet 으로 부른다.
- 예상: 그 실행에서 출력 몫은 기준 단가로 174,833 × $20/백만 = $3.50 이었다. 생각이 절반으로 줄면 117,810 ÷ 2 × $20/백만 = 약 $1.18 이 준다. 모델을 Sonnet 으로 내리면 서브에이전트 몫의 정가 환산이 절반이 된다.
- 틀렸다고 볼 기준: 바꾼 뒤 기록 3번의 서브 출력 중앙값이, 바꾸기 전 새 구조 실행들의 서브 출력 중앙값의 70% 아래로 내려가지 않으면 틀린 것이다. 같은 3번에서 record-lint 차단이 남거나 평가 시나리오 기대를 하나라도 어기면 채택하지 않는다.
- 품질 위험: record 는 코드와 대조해 사실을 쓰는 일이라 정확도가 떨어질 수 있다.
- 상태: 후보 (2026-11-17)

## D-03 늘 실리는 맥락에서 쓰지 않는 것을 뺀다
- 대상: 플러그인 스킬 목록, 커넥터, 도구 정의, 사용자 스킬 설명
- 근거: F-08(첫 호출 60,304 토큰), F-11(최근 30일 호출이 anthropic-skills 9개 가운데 2번, slack 13개 가운데 3번, superpowers 15개 가운데 18번, Notion 플러그인 스킬 10개 0번)
- 방법: (가) 안 쓰는 플러그인 스킬 묶음을 끈다. (나) 안 쓰는 커넥터를 끈다(지연 도구 이름 목록 10,587자, MCP 서버 안내 7,058자). (다) Artifact 도구 정의 36,869자(첫 호출 글자의 23%)를 뺄 수 있는지 확인한다. (라) collect-feedback 의 호출 조건 글을 줄인다(사용자 스킬 6개 설명 1,543자).
- 예상: 줄인 글자 수 × 0.38 토큰이 모든 호출에서 준다. 1만 자를 줄이면 호출마다 약 3,800 토큰, 호출 40번짜리 실행에서 3,800 × 40 = 약 15만 토큰이고 캐시 읽기 기준 단가로 약 $0.03 이다. 새 세션마다 캐시 쓰기 3,800 토큰(약 $0.03)도 준다. 값으로는 작다. 구독 한도가 캐시 읽기를 크게 친다면 달라진다(D-10).
- 틀렸다고 볼 기준: `base` 구성 요소의 글자 수(실측)가 계획한 만큼 줄지 않았거나, 같은 프로젝트 새 세션 5개의 첫 호출 평균이 사전 평균(iic-oms 55,747)보다 예상의 절반도 낮지 않으면 틀린 것이다.
- 품질 위험: 끈 스킬과 도구는 필요할 때 쓸 수 없다. 워크로그 자동 실행은 Notion, Slack 커넥터를 쓴다.
- 드는 것: 설정 변경과 새 세션 다섯 개.
- 상태: 후보 (2026-11-17). 값으로 본 이득이 작아 D-10 의 결과를 본 뒤 정한다. 끄는 방법은 공식 문서로 먼저 확인한다.

## D-04 collect-feedback 한 번의 비용
- 대상: collect-feedback 스킬(포크 실행)
- 근거: F-10(27번, 기준 단가 환산 중앙값 $1.57, 합 $49.34). `stats --skill collect-feedback --since 2026-10-18` → 최근 30일 25번. 11-16 18:30 실행은 호출 28, 출력 84,530 중 생각 69,411, 정가 환산 $3.56. `carry --session f4af52de --agent ae8b384b` → 시작 맥락 50,384 를 28번 읽은 값 36%, 늘어난 맥락 64%. 큰 단계는 사용자 발언 뽑아 보기 +13,743, 색인 읽기와 원본 찾기 +11,414, 볼트 규칙 확인 +21,341, 스타일 폴더 검색 +19,894.
- 방법: 칭찬 한마디마다 도는 호출 조건을 좁힌다. 포크가 세션 원본에서 발언을 찾는 단계를 도구 한 번으로 줄인다. 생각 토큰을 줄인다.
- 품질 위험: 호출 조건을 좁히면 놓친 피드백이 규칙에 반영되지 않는다. 놓친 수는 사용자가 같은 말을 다시 한 횟수로 본다.
- 상태: 먼저 잰다 (2026-11-17). 여러 실행의 `carry` 에서 공통으로 큰 단계를 찾은 뒤 예상과 기준을 쓴다.

## D-05 평가 시나리오를 싸게 돌린다

## D-07 효과 쪽 지표를 만든다
- 대상: 이 연구의 측정 도구
- 근거: 효율은 품질을 지키면서 비용을 줄이는 것이라 품질 신호가 없으면 시도를 채택할 수 없다. 지금은 사후 정정 요청 수를 `after` 로 읽고 손으로 세는 것만 된다.
- 방법: 스타일 색인의 '보강' 횟수(같은 피드백이 다시 나온 수)가 주마다 얼마나 느는지 스타일 저장소 이력에서 센다. record-lint 의 차단과 보고 수의 추이를 남긴다.
- 끝났다고 볼 기준: 보강 수의 주별 추이를 내는 명령이 생기고, attempts 의 실행별 품질 줄을 도구 출력만으로 채울 수 있으면 끝난 것이다.
- 상태: 후보 (2026-11-17)

## D-10 구독 한도 기준으로 잰다
- 대상: 이 연구의 측정 도구
- 근거: F-02 한계(정가 환산은 가중치). 공식 문서의 상태 줄 입력에 `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` 가 있다("Percentage of the 5-hour or 7-day rate limit consumed, from 0 to 100", 구독자에게만 나오고 세션의 첫 응답 뒤부터 나온다). `/usage` 는 "recent usage attributed to skills, subagents, plugins, and individual MCP servers" 를 비율로 보여 준다.
- 방법: 상태 줄 스크립트가 한도 비율을 시각과 함께 파일에 남기게 하고, 실행 전후의 차이를 runs 의 줄과 잇는다.
- 끝났다고 볼 기준: 기록 한 번이 한도를 몇 % 썼는지 runs 의 그 줄과 나란히 적을 수 있으면 끝난 것이다.
- 드는 것: 상태 줄 설정 변경.
- 상태: 후보 (2026-11-17)

## D-11 날마다 도는 자동 실행의 모델을 정한다
- 대상: 워크로그 자동 실행(새 세션에서 collect-worklog)
- 근거: `stats --skill collect-worklog --since 2026-10-20 --not-session 15589b2d --model sonnet` → 5번, 정가 환산 중앙값 $0.52, 기준 단가 환산 중앙값 $1.05. 같은 명령에 `--model opus-5-5` → 9번, $3.05, $3.05. `--model fable` → 9번, $4.37, $1.86. 기준 단가로는 $1.05~$3.05 인 일이 정가로는 모델에 따라 $0.52~$4.37 이 된다.
- 방법: 자동 실행의 모델을 하나로 정한다.
- 품질 위험: 작은 모델은 요약 품질이 떨어질 수 있다. 날마다 워크로그 양이 달라 위 값은 모델 차이만 담지 않는다.
- 상태: 먼저 잰다 (2026-11-17). 워크로그에서 사용자가 고친 곳을 세는 법을 정한 뒤 기준을 쓴다.

## D-13 record 서브에이전트의 호출 수와 맥락 증가
