# 이슈 출처 → Jira 티켓 생성

QA 티켓·스토리·슬랙 스레드·에러 문구를 읽고 원인을 확인한 뒤, 정한 위치에 계획이 담긴 티켓을 만든다. **티켓만 만들고 구현은 하지 않는다**(사용자가 구현을 따로 요청할 때만).

## 입력 — 두 가지만 받는다

| 입력 | 값 | 없으면 |
|---|---|---|
| 생성 위치 | 루트(부모) 티켓 링크 → 그 아래 하위 작업 / "백로그" → 상위 없는 독립 작업 | 세션에서 앞서 받은 루트를 쓴다. 처음이면 한 줄로 묻는다 |
| 참고 대상 | Jira 티켓 링크(QA·스토리) / 슬랙 링크 / 붙여넣은 에러 문구 (여러 개 가능) | 묻는다 |

- 루트는 한 번 받으면 세션 동안 기억한다. 이후 "다음 이슈 <링크>" 는 같은 루트 아래로 만든다
- 요청에 따로 위치를 말하면("백로그로", "OMS-xxxx 하위로") 그 요청만 그 위치로 만든다

## 실행 절차

### 1단계: 참고 대상 읽기
- **Jira 티켓**: `getJiraIssue`(fields: summary, description, status, comment, issuelinks, parent, attachment). 코멘트에 담당자 요구가 붙는 경우가 많다
- **슬랙 링크**: URL 의 `archives/<channel>/p<ts>` 에서 ts 는 `p` 뒤 숫자의 끝 6자리 앞에 `.` 을 넣는다. 링크에 `thread_ts=` 가 있으면 그 스레드를 읽는다(`slack_read_thread`)
  - 부모 메시지 본문이 비어 있으면(봇 알림 "no preview") `slack_read_channel`·검색으로 같은 ts 를 한 번 더 본다. **그래도 비어 있으면 근처 다른 알림으로 대신하지 말고** 에러 문구를 사용자에게 받는다 — 근처 알림은 다른 에러일 수 있다
- **에러 문구**: 붙여넣은 그대로 원인 분석의 출발점으로 쓴다
- 첨부(이미지·엑셀)는 읽지 못했으면 읽지 않았다고 보고에 적는다

### 2단계: 원인 확인 — 짐작으로 쓰지 않는다
- 에러 문구·클래스·메서드로 **원격 기본 브랜치 코드**를 찾는다(`git fetch` 후 `git grep ... origin/<기본 브랜치>`). 로컬 작업 트리는 미커밋 변경이 섞여 있을 수 있다
- 동작이 언제 바뀌었는지는 `git log -S "<문자열>" origin/<기본 브랜치>` 로 커밋·날짜·작성자를 찾는다 (회귀면 원인 커밋을 적는다)
- **이미 다른 티켓·다른 저장소에서 고쳐졌는지** 먼저 본다 — 연관 저장소도 같은 방식으로 grep·log. 고쳐졌으면 "확인 작업" 티켓으로 쓴다
- 실 데이터(주문·클레임 상태)는 읽기 전용 조회로 확인한다. 조회 방법·자격증명 위치는 프로젝트 메모리·시스템 사전을 따른다
- 확인한 것(실측·코드)과 추정을 구분해 둔다 — 티켓 섹션 이름과 보고에 그대로 반영한다

### 3단계: 티켓 작성

**제목**: `[<저장소 접두>] <브랜드·채널> <대상> <현상/작업>` — 접두는 고칠 저장소 기준(형제 티켓 관례를 따른다). 한 줄로 무엇을 고치는지 보이게

**본문** (markdown, 섹션 3개):

```markdown
## 이슈

* <현상 1~3줄, 에러 문구·주문번호 등 식별자 포함>
* 참고: <슬랙 링크>          ← 슬랙·에러 출처일 때만

## 원인                       ← 코드·실측으로 확인했을 때
## 확인된 사항                 ← 원인이 확정 안 됐거나 이미 고쳐진 정황일 때
## 원인 (추정)                 ← 코드 구조로만 추론했을 때

* <메커니즘 — 어떤 조건에서 어느 코드가 왜 실패하는지>
* <언제 바뀌었는지 — 커밋 sha·티켓>

## 작업 내용

* <할 일 불릿>
* <결정이 필요하면 안 나열>
    * 안 1(추천): ...
    * 안 2: ... (단점)
* <재현·확인 항목, 테스트 추가>
```

- 불릿은 평탄하게. 체크리스트(`- [ ]`) 중첩은 쓰지 않는다 — markdown→ADF 변환에서 중첩 task list 가 빠진다. 안 나열 정도의 2단 불릿만 허용
- 계획은 간결하게: 무엇을 바꾸는지 + 확인할 것. 구현 세부(코드 조각)는 넣지 않는다
- 미확인 항목은 숨기지 말고 작업 내용에 "확인" 으로 넣는다

### 4단계: 생성·연결

| 항목 | 하위 작업(루트 지정) | 백로그 |
|---|---|---|
| issueTypeName | `하위 작업` | `작업` |
| parent | 루트 티켓 키 | 없음 |
| 상태 | 기본(할 일) | 기본(할 일), 스프린트 없음 = 백로그 |
| assignee | 사용자 본인 (`atlassianUserInfo` 의 accountId, 루트 티켓 담당자와 같으면 그 값) | 같음 |

연결(`createIssueLink`):

| 참고 대상 | 링크 타입 | 방향 |
|---|---|---|
| QA·버그 티켓 | `Problem/Incident` | inwardIssue = QA 티켓, outwardIssue = 새 티켓 → 새 티켓에 "is caused by <QA>" |
| 스토리·기획 티켓 | `Relates` | 아무 방향 |
| 슬랙·에러 문구 | 연결 없음 | 본문 "참고:" 에 슬랙 URL |

- cloudId 는 티켓 링크의 사이트 주소(`<site>.atlassian.net`)를 그대로 쓴다
- 링크 타입 이름이 다르면 `getIssueLinkTypes` 로 확인한다

### 5단계: 보고 (한국어)

- 첫 줄: 어디에 어떤 키로 만들었는지 + 연결 여부
- 티켓 제목과 링크
- 원인·확인한 사실·할 일 요약 (불릿 3~6줄)
- 마지막: 확인하지 못한 것(추정, 못 읽은 첨부, 결정이 필요한 안)

## 수정 요청이 오면

- "티켓 내용 틀렸어 + 올바른 정보" → 새 티켓을 만들지 않고 같은 키를 `editJiraIssue` 로 제목·본문 교체. 바뀐 원인으로 2단계를 다시 한다
- 이전 내용이 다른 문제였다면, 그 문제를 따로 티켓으로 만들지 보고 끝에 한 줄로 묻는다

## 규칙

- 티켓만 만든다. 코드 수정·커밋은 사용자가 요청할 때만
- 원인은 코드·데이터로 확인한 범위까지만 단정한다. 추정은 섹션 이름(`원인 (추정)`)과 보고에서 밝힌다
- 다른 저장소·다른 사람 티켓으로 이미 해결된 정황이면 수정 티켓이 아니라 확인 티켓으로 쓴다
- 슬랙 본문이 비었을 때 주변 메시지로 추측해 만들지 않는다
