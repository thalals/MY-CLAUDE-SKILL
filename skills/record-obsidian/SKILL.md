# record-obsidian

대화를 Obsidian 볼트에 남기는 순서다. 형식과 세부 규칙은 볼트의 규칙 파일에만 있다. 이 스킬은 순서, 탐색, 검진, 사용자와의 소통을 정한다.

## 원칙

- 볼트는 하나의 뇌다. daily history 는 경위(일화 기억), record 는 지금 참인 사실(의미 기억), index-guide 는 찾아가는 길, proposals 는 구조를 바꾸자는 대화다.
- 기록을 마친 순간, 이번에 쓴 모든 문서는 루트 index-guide 에서 지도만 따라가도 닿아야 한다.
- daily 주제와 record 노트는 서로를 가리킨다.
  - record 를 고친 주제는 처리 기록으로 그 노트를 가리킨다.
  - 대화에서 가져온 사실을 받은 노트는 `sources` 로 그 주제를 가리킨다.
- 동작 사실은 대화가 아니라 origin/develop 코드에서 읽는다.
- 어느 노트가 자리인지, 같은 주제인지, 정책인지 같은 의미 판단은 지도를 읽고 내가 한다. 시각, 커밋, 링크 대조 같은 값은 도구가 낸 것을 쓴다.
- 폴더·노트 종류·시스템 구성, 규칙 파일, 이 스킬은 사용자가 확인한 제안으로만 바꾼다.

## 시작 전

1. `date` 로 오늘 날짜(KST)를 얻는다.
2. 볼트는 `/Users/hyeongminpark/Library/Mobile Documents/iCloud~md~obsidian/Documents/Obsidian` 이다. 경로에 공백이 있어 따옴표로 감싼다. 저장소 경로는 전역 CLAUDE.md '시스템 사전' 에 있다.
3. 아래 파일을 이번 실행에서 새로 읽는다. 규칙이 계속 바뀌므로 기억이나 예전 요약으로 대신하지 않는다.
   - 볼트 루트 `index-guide.md`
   - `daily history/SKILL.md`
   - `record/SKILL.md`
   - 볼트 루트 `proposals.md`(열린 제안과 '마지막 전체 검진')

## 도구

| 도구 | 위치 | 언제 | 내는 것 |
|---|---|---|---|
| `timeline.py` | 이 스킬 폴더 `scripts/timeline.py` | 1단계 | Claude·Codex 원본(jsonl)의 사용자 발언·명령·질문 답변·도구 거절 KST 시각. `--tools` 는 도구 호출, `--span` 은 날짜별 실제 활동 범위 |
| `visit.py` | 볼트 `record/visit.py` | 3·4·6단계 | 열쇠가 적힌 노트·지도·daily, 후보 노트별 basis 이후 커밋, 여러 노트에 걸린 커밋. `--package`, `--fetch`, `--lines`, `--files`, `--all` |
| `record-lint.py` | 볼트 `record/record-lint.py` | 7단계 | 차단 C1~C10, 보고 R1~R7, 저장소별 마지막 fetch |

- 실행은 `python3 "<스킬 폴더>/scripts/timeline.py" …`, `python3 "<볼트>/record/visit.py" …` 로 한다. 스킬 폴더는 이 스킬을 불러올 때 알려 주는 'Base directory' 다. 쓰는 법은 각 파일 머리말에 있다.
- Codex 는 `python3 "<스킬 폴더>/scripts/timeline.py" --session "<Codex jsonl 경로 또는 세션 ID>" --since "MM-DD HH:MM" --span` 으로 읽는다. 원본은 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` 이며, ID 앞부분으로도 찾는다. 경로를 생략하면 기존처럼 현재 디렉터리의 최근 Claude 세션을 읽는다. 주입된 지침·메타 정보와 중복 미러 이벤트는 제외한다.
- 단계마다 필요한 도구만 돌린다. 도구 출력과 기억이 다르면 도구를 따른다.
- 도구를 고치거나 더하면, 볼트 도구는 `record/index-guide` 와 루트 지도에, 스킬 도구는 이 표에 적는다. 스킬 도구를 고치면 스킬 폴더째 iCloud 에 백업한다.
- `scripts/session_hook.py` 는 Claude 훅 전용이다. SessionEnd 는 사용자 발언 3개 이상인 세션의 마지막 실제 활동 시각·원본 경로·종료 시각을 `~/.claude/record-obsidian/pending.tsv` 에 남긴다. SessionStart 는 timeline.py 와 같은 기준으로 원본의 마지막 활동을 다시 읽어 daily sessions 의 끝 시각과 분 단위로 비교한다. 예전 4열 목록도 원본을 찾으면 보정하고, 원본이 없으면 기존 시각을 유지한다. 14일 보관 기준은 실제 종료 시각이다. 설정은 `~/.claude/settings.json` 이며 Codex 훅 설치는 포함하지 않는다.

## 1. daily 를 먼저 쓴다

`daily history/SKILL.md` 의 '절차' 1~7을 따른다.

- 시각은 `timeline.py --since "<기록된 sessions 범위 끝>" --span` 으로 뽑는다. 타임라인 시각과 sessions 범위 끝은 이 출력과 `date` 에서만 가져온다.
- 오늘 파일이 있으면 병합한다. 새 파일로 쓰거나 덮어쓰지 않는다.
  - 같은 내용(같은 티켓, 같은 저장소·목적)은 기존 주제에 넣는다.
  - 같은 질문이나 결정을 다시 다뤘으면 기존 문단을 최신 결론으로 첨삭한다. 주제 설명의 결과·상태 문장도 최신으로 고친다.
- 첨삭은 오늘 파일 안에서만 한다. 지난 날짜 파일은 고치지 않고 `이전 기록:` 링크로 잇는다.
- record 전체 최신화를 요청받았으면, 다른 대화와 함께 왔어도 그 최신화 작업을 오늘 날짜 노트에 따로 주제 하나로 쓴다.

## 2. 주제마다 열쇠를 뽑는다

이번에 쓰거나 고친 주제(H2)마다 세 가지를 적는다.

- 범위 열쇠: 시스템, 패키지 키, 한국어 이름, 엔티티. 지도를 따라 내려갈 때 쓴다.
- 지점 열쇠: 티켓 키, METHOD 경로, 토픽, 클래스·메서드, env 키 이름, 에러 키, 정책 이름. `visit.py` 와 `record/` 검색에 쓴다.
- 사실 갈래: 다음 여섯 가지 중 하나다.
  - 코드 사실
  - 사용자가 정한 규칙(정책)
  - 사용자가 의도라고 한 제약(예외 사항)
  - 고치기로 한 문제(보완 사항)
  - 정하지 않은 것(확인 사항)
  - 대상 아님(작업 환경, 스타일, 도구)

주제가 '대상 아님' 사실뿐이면 3~6단계를 건너뛰고 7단계로 간다. 처리 기록에는 대상 아님으로 남긴다.

## 3. 지도를 따라 내려간다 (B-tree 탐색)

index-guide 는 B-tree 의 내부 노드이고, 지도 줄의 '이럴 때 연다 · 키워드' 가 갈림 열쇠다. 노트는 잎이고, 노트의 H2 는 잎 안의 항목이다.

1. 아래 순서로 내려간다. 지도마다 범위 열쇠가 맞는 줄의 자식만 연다. 여럿이 맞으면 모두 내려간다.
   - 볼트 루트 `index-guide`
   - `record/index-guide`
   - `record/<조직>/index-guide`
   - 시스템 지도
   - 폴더 지도
   - 노트
2. 시스템 지도에 교차 색인이 있으면 그 패키지 줄의 노트를 모두 후보에 넣는다. OMS 는 '패키지별 위치' 다. 한 사실의 상태, 정책, 흐름, 계약은 서로 다른 폴더에 나뉘어 있다.
3. `visit.py <지점 열쇠…> --package <패키지>` 로 열쇠가 적힌 노트와 지도를 한 번에 찾아, 내려가며 놓친 노트를 더한다. '없음' 으로 나온 열쇠는 6단계의 자리 없는 개념으로 넘긴다.
4. 방문 목록을 적는다.
   - 방문 목록은 이번 주제의 사실이 들어갈 노트와, 같은 지점 열쇠가 이미 적힌 노트다.
   - 루트에서 그 노트까지 지나온 지도도 함께 적는다.
   - 4단계는 이 노트들을 고치고, 5단계는 이 경로를 거꾸로 오르고, 6단계는 이 노트들을 검진한다.
5. 갈 곳이 없을 때는 이렇게 한다.
   - 시스템 지도에 설계 전이라고 적혀 있으면(예: OMS-ADAPTER) 그 시스템 내부 사실은 보류한다. 다른 시스템 노트의 상대 쪽 줄에 들어갈 계약 사실은 그 노트에서 처리한다. 그 시스템에 보류가 쌓이면 구조 제안의 '왜' 에 근거를 더한다.
   - 설계된 시스템인데 맞는 노트가 없으면, 그 시스템 '이 폴더의 목적' 노트의 배치 규칙으로 지금 있는 폴더와 노트 종류 안에서 정본 노트를 정한다.
   - 맞는 폴더나 노트 종류가 없으면 구조 제안을 올리고, 그 사실은 확인을 받을 때까지 보류한다.

## 4. 잎에서 upsert 한다

방문 목록의 노트마다 `record/SKILL.md` 의 '갱신 절차' 를 따른다. 거기에 아래 네 가지를 더한다.

- 지난 제안 맞추기: 쓰기 전에, 이번 주제와 맞는 제안이 이미 남아 있는지 찾는다. 제안은 내가 앞서 남긴 추정과 물음이다.
  - 찾는 곳: 방문 노트의 `## 확인 사항` 줄(추정, 의도 미확인, 운영 확인, 정책 후보), daily frontmatter `record` 의 확인 대기·보류 줄(`grep` 으로 열쇠를 찾는다), `proposals.md` 에서 상태가 제안인 항목. 노트 쪽은 `visit.py <열쇠…> --lines` 출력에서 고른다.
  - 맞는 제안이 있으면 그 문장을 근거로 쓰지 않는다. 이번 대화와 origin/develop 코드로 다시 확인한 것만 쓴다.
  - 확인한 내용은 제자리에 쓰고 제안은 없앤다. 코드 사실은 본문, 사용자가 정한 규칙은 정책, 의도라고 한 것은 예외 사항, 고치기로 한 것은 보완 사항이다. 확인 사항 줄은 지운다. 지난 daily 의 확인 대기·보류 줄은 고치지 않고 이번 주제 처리 기록 끝에 `· 정리: <날짜> <주제>` 로 잇는다. proposals 항목은 지우지 않고 상태를 반영·거절로 바꾼다.
  - 다시 확인한 결과가 제안과 다르면 그 차이를 보고에 적는다. 이번 대화로도 정할 수 없는 부분만 지금 근거로 고쳐 쓴 확인 사항 한 줄로 남기고 보고에서 묻는다.
  - 이번 대화의 근거가 origin/develop 에 없어 다시 확인할 수 없으면 그 제안은 그대로 두고, 보고의 정리한 제안에 '다시 확인 못 함' 과 이유를 적는다.
- 최신화
  - `visit.py <지점 열쇠…> --package <패키지> --fetch` 가 방문 노트의 basis 저장소를 fetch 하고 노트별 basis 이후 커밋을 낸다. lint 는 fetch 하지 않는다.
  - 그 커밋을 모두 대조한다. 이번 주제와 무관해 보이는 커밋도 대조한다. 사실이 바뀌었는지는 `--files` 로 바뀐 파일을 보고, 필요한 커밋만 `git show` 로 읽어 판단한다.
  - 반영할 사실을 반영한다. 커밋을 모두 대조했으면 사실 연산이 변경 없음이어도 basis 와 verified 를 올린다.
  - 다 보지 못했으면 basis 를 올리지 않고, 남은 커밋을 보고에 적는다.
  - record 전체 최신화를 요청받았으면 `visit.py --all --fetch` 의 모든 노트가 방문 목록이다. 여러 노트에 걸린 커밋은 '커밋별 노트' 로 한 번만 읽는다.
- 출처 잇기
  - 노트에 쓴 사실이나 이유를 daily 주제에서 가져왔으면 frontmatter `sources` 에 그 주제 링크를 더한다. 사용자 결정, 의도·제약 확인, 티켓 판정, 대화에서 확인한 코드 사실이 여기에 든다.
  - 커밋 대조로만 고친 노트에는 더하지 않는다. 그 근거는 basis 와 변경 이력이다.
- 넘침: 노트 본문이 200줄을 넘게 되면 나누기 전에 구조 제안을 올린다. 확인을 받기 전에는 넘칠 사실을 그 노트에 넣지 않고 처리 기록에 보류로 남긴다.

## 5. 지나온 지도를 거슬러 고친다

방문 경로를 노트에서 루트 쪽으로 거슬러 오른다. 지도마다 그 지도가 가리키는 자식의 범위가 바뀌었는지 본다.

범위는 지도 줄이 가리키는 것이다.
- 노트와 폴더
- 기능 H2 제목
- 정책의 대분류·중분류·정책 이름
- 상대 시스템
- 지도 형식이 키워드로 쓰는 말(패키지 키, 한국어 이름, 대표 엔티티)

본문 사실 때문에 이것이 생기거나, 없어지거나, 이름이 바뀌었을 때만 범위가 바뀐 것이다. 확인 사항, 보완 사항, 진행 중에만 있는 말은 지도에 올리지 않는다.

범위가 바뀌었으면 이렇게 한다.
- 그 줄의 설명과 키워드를 고친다. 그 지도의 요약 목록도 함께 고친다(OMS 지도의 기능 목록, domain 지도의 policy 줄).
- 지도 없는 데이터 폴더(OMS `domain/entity`·`domain/policy`, daily history 의 연·월 폴더)의 노트는 가장 가까운 상위 지도가 관리한다. 그 노트를 만들거나 옮기면 그 상위 지도의 줄을 고친다.
- 지도가 100줄을 넘으면 세부를 아래 지도로 내린다.

범위가 바뀌지 않았으면 그 지도에서 멈추고, 위의 지도도 고치지 않는다. 폴더를 만들거나 바꾸는 일은 구조 제안으로 확인을 받은 뒤에만 한다.

## 6. 검진한다

방문 목록에 llm-wiki 점검 여섯 가지(Karpathy)를 한다. 규칙 안에서 고칠 수 있는 것은 고치고, 정할 수 없는 것은 확인 사항이나 보고로, 구조가 맞지 않는 것은 구조 제안으로 보낸다.

| 점검 | 보는 법 | 찾으면 |
|---|---|---|
| 모순 | `visit.py <열쇠…> --lines` 로 같은 열쇠가 나온 줄을 노트끼리 비교한다 | 코드로 정해 대체한다. 못 정하면 확인 사항에 쓴다 |
| 낡은 주장 | 4단계 표류 대조. 열쇠가 나온 daily 날짜가 노트 verified 보다 늦은데 노트에 없는 결정 | 반영하거나 확인 사항에 쓴다 |
| 고아 | lint C1·C2 | 지도에 올린다 |
| 자리 없는 개념 | `visit.py` 가 '없음' 으로 낸 열쇠, 시스템 지도 교차 색인에 없는 패키지 | 배치 규칙 안에서 노트를 정한다. 자리가 없으면 구조 제안 |
| 빠진 교차 참조 | 같은 패키지의 다른 면 노트(교차 색인 줄)가 이 사실을 상대 쪽·관련 줄로 서로 가리키는지 | 잇는다 |
| 메울 수 있는 빈칸 | 방문 노트의 확인 사항 가운데 지금 코드·커밋으로 답할 수 있는 것(이번 주제와 맞는 것은 4단계 지난 제안 맞추기에서 이미 처리) | 답을 본문에 쓰고 그 줄을 옮긴다. 사용자 판단이 필요하면 보고에서 묻는다 |

- 매 실행은 방문 목록만 본다. 볼트 전체 검진은 사용자가 요청할 때 `visit.py --all --fetch` 와 같은 여섯 가지로 하고, 마치면 `proposals.md` 의 '마지막 전체 검진' 날짜를 고친다.
- '마지막 전체 검진' 이 없거나 7일보다 오래됐으면 보고 끝에서 전체 검진을 할지 묻는다.

## 7. 잇고 점검한다

1. 날짜 노트 frontmatter `record` 에 주제마다 처리 결과를 한 줄씩 쓴다. 형식은 `record/SKILL.md` '처리 기록' 에 있다. 방문 노트의 표류를 대조해 고친 노트는 그 주제 줄 끝에 `· 표류 대조: <노트>(<연산>)` 로 덧붙인다.
2. `python3 "<볼트>/record/record-lint.py"` 를 돌린다. 차단이 0 이 될 때까지 고친다.
3. lint 가 보지 않는 것을 점검한다.
   - 이번에 쓴 날짜 노트가 daily `index-guide` 와 `date-guide` 양쪽에 링크돼 있다.
   - 고친 노트의 머리 요약, 목차, 지도 줄이 지금 내용과 맞다.
   - 새로 생긴 말(기능 이름, 정책 이름, 티켓 키)은 지도를 따라 내려가거나 검색해서 찾을 수 있다.

## 8. 보고한다

표 하나에 단계마다 고친 파일과 한 일을 적는다.

| 단계 | 적을 것 |
|---|---|
| daily | 주제, 병합인지 추가인지 |
| record | 노트, 연산, basis 변화 |
| 지도 | 고친 지도와 이유. 고치지 않았으면 그 이유 |
| 검진 | 여섯 가지 점검에서 찾은 것과 처리 |
| lint | 차단 수, 보고 R1~R7 |

표 아래에는 정리한 제안과 사용자가 정할 것을 적는다.
- 정리한 제안: 4단계에서 맞춘 제안마다 한 줄. 어디의 무슨 제안이었는지, 다시 확인한 결과를 어디에 썼는지, 제안과 달랐던 점. 없으면 '없음'
- 서술과 다름
- 확인하지 못한 결과
- 보류
- 다 보지 못한 커밋
- 판단이 필요한 확인 사항
- 열린 제안: `proposals.md` 에서 상태가 제안인 것을 한 줄씩. 이번에 새로 올렸거나 근거를 더한 것을 표시한다

## 구조 제안과 소통

제안 대기열은 볼트 루트 `proposals.md` 다. 대화로만 말한 제안은 다음 세션이 모르므로 여기에 남긴다.

올리는 때:
- 기록할 사실이 지금 사전 목록(시스템 폴더, 폴더, 노트 종류, 배치 규칙)에 맞지 않을 때
- 한 시스템에 보류가 쌓일 때
- 노트를 나눠야 할 때
- 사용자가 구조를 바꾸자고 했을 때
- 기록하다 규칙 파일이나 이 스킬의 빈틈을 찾았을 때

제안 하나는 H2 하나다(`## YYYY-MM-DD <제목>`, 목차에도 더한다). 줄 머리는 이 차례다.
- `- 종류:` 구조, 규칙, 스킬 가운데 하나
- `- 왜:` 맞지 않는 내용과 근거(daily 주제·노트 링크, 사용자 발언 시각)
- `- 제안:` 바꿀 폴더 트리, 옮길 노트, 지도, 규칙 문장
- `- 영향:` 옮길 노트 수, 고칠 링크 수(실측), 바뀔 규칙·점검, 검토 의견
- `- 정할 것:` 사용자가 고를 것(있을 때)
- `- 상태:` 제안, 반영, 보류, 거절 가운데 하나와 날짜
- `- 결정:` 확인을 받은 날짜와 그 daily 주제 링크(확인 뒤)

순서:
1. 제안을 쓰고 보고에서 묻는다.
2. 사용자가 확인하면 반영한다. 구조는 노트·지도·루트 지도·규칙·점검까지, 규칙은 그 파일, 스킬은 SKILL.md 와 iCloud 백업까지 한 번에 고친다.
3. 상태를 반영으로 바꾸고 결정 줄을 단다.
4. 그 일을 daily 에 기록한다.

- 같은 문제의 제안이 이미 있으면 새로 쓰지 않고 그 제안의 '왜' 에 근거를 더한다.
- 거절이나 보류도 지우지 않고 상태만 바꾼다.

## 스킬을 고칠 때

- 이 스킬과 도구는 사용자가 확인한 제안으로만 고친다(구조 제안과 소통).
- 고친 뒤 `evals/scenarios.md` 의 시나리오(A·B·C)를 서브에이전트로 다시 돌려 기대 결과와 비교한다. 어긴 것은 문장을 고치고 다시 돌린다.
- 타임라인·알림 도구를 고치면 `python3 -B "<스킬 폴더>/evals/test_session_tools.py"` 로 두 원본 형식, 활동 시각, 기존 알림 이행을 검증한다. 시험은 임시 입력과 별도 상태 파일만 사용한다.
- 스킬 폴더째(SKILL.md, scripts, evals) iCloud `claude/skills/record-obsidian/` 에 백업한다.

## 지키는 것

- 저장소는 읽기만 한다(`git fetch`, `log`, `show`, `merge-base`). 커밋, 브랜치 이동, push 는 하지 않는다.
- env/*, *.env, *private* 파일은 열지 않는다. 비밀값, URL, 호스트명은 쓰지 않는다.
- 여러 파일을 에이전트들에 나눠 고치게 할 때는 이렇게 한다.
  - `<볼트>/.record-staging/` 에 복사해 고친다. `/tmp` 는 쓰지 않는다.
  - lint 를 통과시킨 뒤 볼트에 반영하고 staging 폴더를 지운다.
  - 반영 직전에, 그사이 사용자가 볼트 파일을 고쳤는지 비교한다.
