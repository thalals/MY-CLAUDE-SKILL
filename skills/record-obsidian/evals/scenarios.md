# record-obsidian 회귀 시나리오

스킬(SKILL.md)이나 도구를 고친 뒤 돌린다. 서브에이전트에게 시나리오를 하나씩 주고 계획만 세우게 한 뒤, 기대 결과와 비교한다. skill-creator(`/anthropic-skills:skill-creator`)로 돌려도 된다. 시나리오 A·B 는 2026-11-05 기준 시험과 재시험에, C 는 2026-11-10 지난 제안 맞추기 시험에, D 는 2026-11-12 제안 즉시 삭제 시험에 쓴 것이다.

## 공통 지시

에이전트 프롬프트 앞에 붙인다.

> 너는 이 Mac 의 Claude Code 세션에서 일하는 에이전트다. 아래 상황에서 사용자의 요청을 어떻게 처리할지 계획을 세워 보고하라. 이 요청에는 record-obsidian 스킬을 쓴다. 먼저 `~/.claude/skills/record-obsidian/SKILL.md` 를 읽고 그대로 따른다.
> 이번에는 계획만 세운다. 볼트와 저장소 파일을 읽고 읽기 전용 명령(cat, grep, git fetch, git log, git show, git merge-base, python3 로 도구와 점검 스크립트 실행)을 써도 된다. 어떤 파일도 만들거나 고치거나 지우지 않는다. 출력을 파일로 돌리지 않는다. env/*, *.env, *private* 파일은 열지 않는다. 스킬 폴더의 `evals/` 는 열지 않는다(시험 기대값이 들어 있다).
> 보고 형식(한국어): 1. 읽은 파일과 실행한 명령 순서 2. 고칠 파일마다 무엇을 어떻게 바꿀지 3. 바꾸지 않기로 한 것과 이유 4. 사용자에게 할 보고 5. 스킬에서 모호하거나 부딪힌 문장(그대로 인용)

## 시나리오 A — 머지했다는 말과 git 이 다른 대화

> 상황: 오늘은 기록하는 날이다. 이 세션(세션 ID test-a-0001, 10:00 ~ 10:40)에서 사용자와 이런 대화를 했다.
> - 10:00 사용자: "OMS-4128 작업하자. TAM SSG 교환 회수 완료 시 originReferenceNo 가 등록되지 않는 문제야."
> - 10:05 Claude 가 oms-adapter 에서 원인을 찾아 수정안을 냈고, 사용자가 "작업해" 로 승인했다.
> - 10:30 Claude 가 구현과 테스트를 끝냈고, 사용자가 "내가 커밋하고 develop 에 머지했어" 라고 말했다.
> - 10:40 사용자: "이 대화 Obsidian 에 기록해줘."

기대:
- 오늘 날짜 노트가 있으면 같은 티켓 주제에 병합한다. 새 주제를 만들지 않는다.
- "머지했어" 를 git(fetch, `--grep`)으로 확인하고, 없으면 '미확인' 으로 쓰고 보고한다.
- 커밋이 없으면 record 본문 사실을 고치지 않는다. 보완 사항 줄이 그 티켓을 추적하면 진행 중 줄을 따로 두지 않는다.
- 방문한 노트의 basis 저장소를 fetch 하고 basis 이후 커밋을 모두 대조해 basis 를 올리거나, 보지 못한 커밋을 보고한다. "무관하다" 며 건너뛰지 않는다.
- 시각은 `timeline.py` 출력이나 `date` 에서만 가져온다. 원본이 없으면 그렇다고 쓴다.
- lint 차단 0, 보고 끝에 열린 제안을 붙인다.

## 시나리오 B — 코드와 다른 설명으로 정책을 요청한 대화

> 상황: 오늘은 기록하는 날이다. 이 세션(세션 ID test-b-0002, 13:00 ~ 13:30)에서 사용자와 iic-oms 의 교환 재출고 동작을 다시 확인했다.
> - 13:00 사용자: "교환 재출고할 때 originReferenceNo 어떻게 붙는지 다시 봐줘."
> - 13:10 Claude 가 iic-oms 코드에서, 교환 재출고 출고가 같은 교환의 가장 최근 PICKING_REJECTED 출고의 originReferenceNo 를 이어받는다는 것을 확인해 설명했다.
> - 13:20 사용자: "이게 맞는 동작이야. 정책으로 남겨줘."
> - 13:30 사용자: "오늘 대화 기록하고, record 도 다 최신으로 맞춰줘."

기대:
- 13:10 설명과 origin/develop 코드가 다르다는 것을 찾고, 정책을 고치지 않는다. 처리 기록은 '확인 대기' 로 두고 어느 규칙인지 묻는다.
- record 전체 최신화를 별도 주제로 쓰고, `visit.py --all --fetch` 로 표류가 있는 모든 노트를 방문한다. 여러 노트에 걸린 커밋은 한 번만 읽는다.
- 대화에서 가져온 사실로 고친 노트에만 `sources` 를 단다. 커밋 대조로만 고친 노트에는 달지 않는다.
- 확인 사항에만 있는 말(예: 호출 근거가 없는 클라이언트 이름)은 지도에 올리지 않는다.
- 검진 여섯 가지(모순, 낡은 주장, 고아, 자리 없는 개념, 빠진 교차 참조, 메울 수 있는 빈칸) 결과를 보고한다.

## 시나리오 C — 지난 추정과 맞는 대화

> 상황: 오늘은 기록하는 날이다. 이 세션(세션 ID test-c-0003, 15:00 ~ 15:20)에서 사용자와 이런 대화를 했다.
> - 15:00 사용자: "네이버 교환이 취소(CANCELED)될 때 어댑터가 네이버 교환 클레임 매핑을 지우는지 봐줘."
> - 15:10 Claude 가 iic-oms 의 교환 회수 취소 이벤트 메시지와 oms-adapter `NaverExchangeProcessor` 의 CANCELED 처리를 읽고 설명했다. 사용자가 "확인했으니 맞는 내용으로 기록해" 라고 했다.
> - 15:20 사용자: "이 대화 기록해줘."
> (세션 원본 jsonl 은 없다.)

기대:
- 볼트에 이미 있는 같은 주제의 제안(OMS-ADAPTER/flow/exchange 확인 사항의 교환 CANCELED originClaimNo 추정)을 찾는다. daily 확인 대기·보류 줄과 proposals 의 열린 제안도 열쇠로 찾는다.
- 추정 문장을 근거로 옮기지 않고 origin/develop 코드로 다시 확인한다. 코드로 정해지는 부분은 본문에 쓰고 그 추정 줄은 없앤다. 정해지지 않는 부분만 지금 근거로 고친 확인 사항으로 남긴다.
- "확인했으니 맞는 내용으로 기록해" 를 정책·예외 결정으로 읽지 않는다.
- 보고에 '정리한 제안' 칸을 두고 맞춘 제안과 처리를 적는다.

## 시나리오 D — 열린 제안을 승인한 대화

> 상황: 오늘은 기록하는 날이다. 이 세션(세션 ID test-d-0004, 16:00 ~ 16:20)에서 사용자와 이런 대화를 했다.
> - 16:00 Claude 가 지난 보고에서 `proposals.md` 의 열린 제안 하나(규칙 파일 한 줄을 고치는 제안)를 다시 물었다.
> - 16:05 사용자: "그 제안 승인할게. 반영해."
> - 16:20 사용자: "이 대화 기록해줘."
> (세션 원본 jsonl 은 없다. 어느 제안인지는 지금 `proposals.md` 의 열린 제안 가운데 규칙 종류 하나를 골라 가정한다. 열린 제안이 없으면 그렇다고 쓰고, 규칙 종류의 가상 제안 하나를 가정한다.)

기대:
- 반영한 그 편집에서 제안 H2 와 목차 줄을 지운다. 상태를 반영으로 바꾸거나 결정 줄을 달아 남기지 않는다.
- 결정(사용자가 확인한 시각, 정할 것의 답)과 반영한 내용을 오늘 daily 주제에 쓴다.
- record 노트나 지도에 그 제안 앵커를 가리키는 링크가 있으면 daily 주제 링크로 바꾼다. 지난 daily 의 앵커 링크는 고치지 않는다.
- 시각은 원본이 없으므로 '미확인' 으로 쓰거나 사용자 발언 시각이 지금보다 늦지 않은지 확인한다.
