# Collect Feedback

대화 중 사용자가 준 피드백을 수집하여 스타일 폴더에 반영한다.

## 스타일 폴더 구조 (2026-11-10)

```
/Users/hyeongminpark/Library/Mobile Documents/com~apple~CloudDocs/claude/style/
  index.md     매 세션 읽는 색인. 읽는 법, 우선순위 두 블록(작업 방식·코드), 파일 목록(자동 생성)
  code/*.md    코드 규칙 주제 파일
  work/*.md    작업 방식 주제 파일
```

- 세션은 `index.md` 만 항상 읽고, 주제 파일은 작업에 맞는 것만 읽는다. 그래서 **규칙은 그 규칙이 필요한 작업의 파일에 둔다** — 분류 기준은 "무엇에 대한 규칙인가" 가 아니라 "어떤 작업을 할 때 읽혀야 하는가" 다.
- 주제 파일의 머리는 `# 제목`, 빈 줄, `> 읽는 때: <작업>. 색인은 \`index.md\`.` 이다. 이 인용 줄과 `### ` 제목에서 색인의 파일 목록이 만들어지므로 형식을 바꾸지 않는다.
- 주제 파일 안에서 코드 규칙은 섹션 없이 위에, 작업 방식 규칙은 `## 하지 말아야 할 것` / `## 더 신경써야 할 것` / `## 잘한 것 / 유지할 것` 섹션 아래에 둔다.
- 색인의 파일 목록은 `python3 ~/.claude/skills/collect-feedback/scripts/build_index.py` 가 만든다. 손으로 고치지 않는다.
- 색인의 '작업별 최소 세트' 표(작업 → 반드시 읽을 파일 → 해당하면 읽을 파일)는 손으로 관리한다. 주제 파일을 더하거나 나누거나 '읽는 때' 를 바꾸면 같은 편집에서 이 표를 고치고, 표의 '반드시' 칸에 파일을 더하는 것은 매 작업의 읽는 양을 늘리므로 보고에 제안으로만 남긴다 (사용자 승인 후 반영).
- 색인은 애매하면 작업 전에 사용자에게 읽을 파일을 묻게 한다 (사용자 지시 2026-11-10). 같은 종류의 작업에서 이 질문이 반복됐다는 피드백이 오면 그 작업을 표의 새 행으로 제안한다.
- 옛 통합 파일(`code_style.md`, `feedback_work_style.md`, `test_work_style.md`)은 `style-archive/2026-11-10-pre-split-*` 에 있다. 다시 만들지 않는다.

## 호출 시점

트리거 조건은 frontmatter `when_to_use` 참조 — **여기가 트리거의 단일 소스다 (2026-09-02).** CLAUDE.md·스타일 파일에 트리거 목록을 중복 기재하지 않으며, 트리거 변경은 frontmatter 만 수정한다.

**트리거 누락 안티패턴 (실제 발생, 반복 금지):** "잘했어" → 단순 응답으로만 처리 → 사용자가 "칭찬을 했는데 피드백 수집할게 없나보네 ?" 로 두 번 알려야 실행. 칭찬 메시지를 받으면 응답 텍스트를 쓰기 전에 먼저 이 스킬을 호출하고, 결과 보고에 칭찬 응답을 통합한다.

## 실행 절차

1. **대화 스캔** — 위 수집 대상에 해당하는 발언을 모두 찾는다
2. **분류** — `index.md` 를 읽고, 파일 목록의 '읽는 때' 와 규칙 제목으로 각 항목이 들어갈 주제 파일을 고른다 (아래 "분류 기준 상세" 참조). 주제 파일 전체를 미리 읽지 않는다
3. **기존 항목 검색** — 신규 항목을 쓰기 전에 스타일 폴더 전체에서 실행한다:
   ```bash
   grep -rn "<핵심키워드>" "<style 폴더>" --include="*.md"
   ```
   피드백의 핵심 키워드(예: `nullable`, `네이밍`, `DTO`, `테스트`)뿐 아니라 유사 개념(동의어·상위 개념·관련 도메인 용어)까지 2~3회 검색하고, 색인의 규칙 제목 목록도 훑는다. 같은 규칙이 다른 주제 파일에 이미 있으면 그 파일이 대상이다.
4. **대상 파일 읽기 + 크기 측정** — 고른 주제 파일만 읽고 `wc -c` 로 크기를 확인한다 (아래 "파일 크기 관리" 참조). 줄 수(`wc -l`)가 아니라 바이트가 기준 — 한 줄이 길어지는 비대는 줄 수로 안 잡힌다. "정확히 같은 규칙"만 찾는 것이 아니라 **병합 후보**를 찾는 것이 목적이다. 이 결과를 5번 판단의 근거로 쓴다.
5. **반영 방식 결정** — 병합 우선, 신규는 마지막 수단 (사용자 지시 2026-09-02):

   | 상황 | 방식 |
   |------|------|
   | 같은 규칙 / 비슷한 내용 / 기존 항목을 강화(구체화·확장·예외·반례 추가)하는 피드백 | **보강** — 기존 항목에 통합. 새 내용은 하위 불릿 1줄 또는 본문 문장에 흡수, 제목 괄호의 보강 횟수를 +1 하고 최근일을 보강일로 갱신 (예: `(2026-05-08, 보강 1 · 최근 06-18)` → `(2026-05-08, 보강 2 · 최근 07-02)`). 통합 후 8줄 초과 시 상위 개념으로 압축 |
   | 새 피드백과 관련된 기존 항목이 2개 이상 흩어져 있음 | **병합 제안** — 새 피드백은 가장 가까운 항목에 즉시 보강하고, 흩어진 기존 항목들의 통합안은 보고에 제안으로 남긴다 (기존 항목 재구성은 사용자 승인 후) |
   | 기존 어떤 항목과도 연결되지 않음 | **신규** — 아래 항목 작성 규격에 맞춰 해당 섹션에 추가 |

   보강 vs 신규가 애매하면 **보강**을 택한다 — 유사 규칙의 신규 누적이 파일 비대의 주 원인이다. 수집할 피드백이 없으면 "수집할 피드백이 없습니다" 로 종료한다.
6. **파일 수정** — Edit 도구로 주제 파일을 업데이트. 보강/신규가 우선순위 테마에 속하면 `index.md` 우선순위 블록의 수치도 갱신 (아래 "우선순위 블록 관리" 참조)
7. **색인 갱신** — 항목을 더했거나 제목을 바꿨으면 `python3 ~/.claude/skills/collect-feedback/scripts/build_index.py` 를 실행한다. 출력의 파일별 크기와 상한 초과 알림을 보고에 쓴다
8. **결과 보고** — 아래 "결과 보고 형식" 준수

## 항목 작성 규격

각 항목은 다음 구성만 포함한다:

```markdown
### <규칙을 한 줄로 (YYYY-MM-DD)>

- **무엇:** 지켜야 할 동작 1~2줄
- **왜:** 근거 1줄
- (필요시) 코드 예시 3줄 이하
```

- **제목 괄호 표기 (2026-11-10):** `(최초일, 보강 N · 최근 MM-DD, 정정 N · 최근 MM-DD, 병합 N · 최근 MM-DD)` — 날짜를 나열하지 않고 횟수와 최근일만 적는다. 해당 없는 구분은 생략하고 순서는 보강 → 정정 → 병합. 병합된 항목의 최초일은 가장 이른 하나만 남긴다
- **본문 8줄 이하.** 넘으면 규칙이 두 개 이상 섞여 있다는 신호 — 분리하거나 상위 개념으로 압축한다
- 세션 고유 맥락(티켓 번호, 특정 파일 경로, 대화 재현)은 넣지 않는다 — 다음 세션에서 self-contained 하게 읽혀야 한다
- **"사용자 피드백 흐름" 대화 재현·사용자 원문 인용은 파일에 넣지 않는다** — 시그널 원문은 결과 보고(표)에만 표시. 파일에는 일반화된 규칙만 남긴다
- **칭찬 항목도 동일 규격.** "Why good / How to apply" 장문 서술 금지 — 왜 칭찬받았는지 분석해 다른 항목과 같은 규칙 형태(제목/무엇/왜)로 압축한다. 칭찬받은 행동이 기존 규칙에 이미 커버되면 신규 대신 **보강**(제목 괄호의 보강 횟수·최근일 갱신 + 하위 불릿 1줄)
- 장문 배경 서술 대신 결론을 쓴다

## 파일 크기 관리

4번 단계에서 측정한 주제 파일 크기(`wc -c`)에 따라 동작이 달라진다:

| 주제 파일 크기 | 동작 |
|------|------|
| ~15KB | 정상. 그대로 추가 |
| 15~20KB | 신규 추가 전 3번 검색 범위를 넓혀 병합 가능 항목을 우선 찾는다 |
| 20KB 초과 | 결과 보고에 **파일 분할 제안 1줄**(어느 항목을 어떤 '읽는 때' 의 새 파일로 뺄지)을 포함한다. 분할은 사용자 승인 후 |

- 크기가 넘으면 압축보다 분할이 먼저다 — 압축은 반례·경위를 깎고, 분할은 규칙을 그대로 둔 채 읽는 양만 줄인다. 압축은 한 파일 안에 같은 주제의 중복 서술이 쌓였을 때만 제안한다.
- `index.md` 는 매 세션 로드되므로 12KB 안팎으로 둔다. 규칙 본문·예시를 색인에 쓰지 않는다. 15KB 를 넘으면 보고에 알린다.
- 같은 규칙을 두 파일에 쓰는 것이 가장 비싼 실수다. 두 작업에 모두 필요한 규칙은 더 자주 읽히는 파일 한 곳에 두고, 다른 파일에서는 `"제목" 항목` 으로 가리킨다.

### 분할 절차 — 사용자 승인 후에만

1. 새 주제 파일을 머리 형식(`# 제목`, `> 읽는 때: … . 색인은 \`index.md\`.`)으로 만들고 항목을 본문 그대로 옮긴다 (고쳐 쓰지 않는다)
2. 옮긴 항목을 `"제목" 항목` 으로 가리키던 문장에 파일 이름이 적혀 있으면 고친다 (`grep -rn "<옛 파일 이름>"`)
3. `build_index.py` 를 실행하고, 옮긴 항목 수 before/after 를 보고한다

### 압축(compaction) 절차 — 사용자 승인 후에만

1. **아카이브 스냅샷** — 원본을 `style-archive/YYYY-MM-DD-<폴더>-<파일명>` 으로 복사 (정보 보존 보장)
   ```
   /Users/hyeongminpark/Library/Mobile Documents/com~apple~CloudDocs/claude/style-archive/
   ```
2. **규격 재적용** — 전 항목을 "항목 작성 규격"에 맞춰 재작성 (대화 재현·장문 How-to-apply 제거, 규칙 유실 금지)
3. **병합** — 같은 주제의 흩어진 항목 통합, 타 파일과의 중복 항목은 한 곳만 유지
4. **검증 + 보고** — `grep -c "^### "` 로 항목 수 before/after 비교, 제거/병합된 항목은 각각 사유(어디로 병합됐는지 / 어느 항목과 중복인지)를 표로 보고

`style-archive/` 는 세션 컨텍스트에 로드되지 않는다 (CLAUDE.md 의 스타일 참조 경로는 `style/index.md` 와 그 색인이 가리키는 주제 파일만 해당). 2026-11-10 에 통합 파일 3개(127KB)를 색인 + 주제 파일 16개(파일당 3~13KB, 색인 11.8KB)로 나눴다 — 항목 104개를 본문 그대로 옮겼다. 그 전의 압축: 2026-09-02 (feedback 105KB→29KB, code 116KB→39KB), 2026-10-28 (code 61.7KB→50.2KB, 항목 98→61 병합), 2026-11-06 (feedback 68.4KB→59.6KB, 항목 65→62, code 61.4KB→60.0KB, 항목 62 유지 — 규칙이 빽빽해 서사 정리로는 한계), 2026-11-10 (feedback 60.1KB→58.0KB, 항목 62→50, code 60.7KB→60.9KB, 항목 62→51 — feedback 의 코드 규칙 4건을 code 로 옮겼고, 제목 날짜 목록을 횟수·최근일 표기로 바꿨으나 크기는 줄지 않음(파일당 +0.2KB)).

## 우선순위 블록 관리

`index.md` 의 "우선순위 — 작업 방식" / "우선순위 — 코드" 두 블록은 사용자가 자주 반복한 피드백 테마의 순위표다 (사용자 지시 2026-09-02). 반복 = 사용자가 여러 번 말해야 했다는 뜻이므로, 순위가 높을수록 작업 중 우선 준수한다.

- **산정 기준:** 관련 룰 수 + 보강 횟수, 동률이면 최근 반복 시점이 위. 표기: `(룰 n · 보강 m · 최근 MM월)`
- **갱신 (자동):** 보강/신규 반영 시 해당 테마의 룰 수·보강 수·최근 시점을 갱신한다. 수치는 증분 유지하고, 압축(compaction) 때 전체 재산정으로 보정
- **순위 변경 (제안):** 수치 갱신으로 순위 역전이 생기면 임의 재배열하지 않고 결과 보고에 "순위 변동 제안 1줄" — 사용자 승인 후 재배열
- **새 테마 (제안):** 어느 테마에도 안 속하는 룰이 같은 성격으로 3개 이상 모이면 새 테마 후보로 보고에 제안. 테마 수 상한은 블록당 7개 — 초과 시 최하위 테마와 교체 제안
- **테마는 룰이 아니다** — 규칙 본문은 각 항목에만 두고, 우선순위 블록은 테마명 + 1줄 요지 + 수치만 유지한다

## 결과 보고 형식

사용자가 판단할 수 있도록 아래를 모두 포함한다:

- **각 파일별 표** — 변경이 있는 파일마다 `| 섹션 | 항목 | 시그널 | 방식 |` 표로 정리 (추가 항목 + 사용자 원문 시그널 + 보강/병합/신규 구분)
- **파일 크기 1줄** — 변경한 주제 파일마다 `변경 전 → 변경 후` KB 와 `index.md` 크기. 주제 파일 20KB 초과 시 분할 제안 포함
- **우선순위 영향 1줄** — 보강/신규가 속한 테마와 수치 변화 (예: "측정·증거 우선: 룰 9→10"). 순위 역전·새 테마 후보가 생기면 변동 제안 포함
- **추가 없는 파일도 한 줄 표시** — "변경 없음" 만 쓰지 말고 사유 1줄 (예: "이번 대화의 코드 룰들은 작업 판단 기준 성격이라 `work/scope.md` 로 분류") — 변경 없는 주제 파일을 모두 나열하지 않고 `code/`·`work/` 폴더 단위로 한 줄
- **헷갈릴 수 있는 분류는 근거 명시** — 같은 항목이 다른 파일에 들어갈 가능성이 있으면 왜 그 파일을 선택했는지 1줄 사유. 사용자가 분류 적정성을 즉시 판단 가능해야 함
- **사용자 피드백 (2026-05-15):** "이런 반영결과와 각 style.md 에 대한 선택 기준을 알려주니까 판단하기 좋네 앞으로도 이렇게 해줘"
- **사용자 기준 (2026-11-10):** 필요한 정보만 읽고, 조회가 빠르고, 토큰을 아낀다 — 규칙 배치와 색인 크기는 이 세 가지로 판단한다

## 분류 기준 상세

주제 파일의 정확한 목록과 '읽는 때' 는 `index.md` 의 파일 목록이 단일 소스다. 아래는 고르는 기준이다.

| 폴더 | 다루는 영역 |
|------|------------|
| `code/` | 코드 파일을 쓰거나 고칠 때 필요한 규칙 — Kotlin 문법, 네이밍, 구조·추출, 도메인 로직, 예외·무결성, 외부 연동, Kafka·DynamoDB, 테스트 코드. 그 코드 작업에 붙는 작업 방식 규칙(예: 외부 API 를 붙이기 전 공식 문서 검증)도 같은 파일의 작업 방식 섹션에 둔다 |
| `work/` | 코드 종류와 무관한 작업 방식 — 요청 범위·해석, 결정 위임, 보고·답변 형식, 검증·디버깅, git·파일 조작, 문서·기록, 작업 프로세스, QA 시나리오 |

- 테스트 코드(Kotest 등) 작성 룰 = `code/test.md`. 테스트 시나리오/QA 프로세스 룰 = `work/qa-scenario.md`. 헷갈리면 "이게 코드 파일을 건드리는가, 테스트 시나리오/QA 문서를 건드리는가" 로 구분.
- 어느 파일의 '읽는 때' 에도 맞지 않으면 가장 가까운 파일에 넣고 보고에 새 주제 파일 제안을 남긴다 — 파일을 임의로 만들지 않는다.

## 실행 컨텍스트 제약

이 스킬은 `context: fork` 로 서브에이전트에서 실행된다. 부모 대화 이력은 전부 상속되는 것이 전제라 대화 스캔은 정상 동작해야 하지만, **메인 세션으로 돌아가는 것은 마지막 assistant 메시지 하나뿐이다.**

- **상속 fallback (2026-10-07):** fork 에 사용자 발언이 하나도 없으면(스킬 본문·시스템 리마인더만 보임) "피드백 없음"으로 끝내지 말고 세션 transcript `~/.claude/projects/<project-dir>/<session-id>.jsonl` 을 읽어 `type == "user"` 의 text 발언을 스캔한다 — `<session-id>` 는 scratchpad 경로의 UUID, `<project-dir>` 는 cwd 의 `/` 를 `-` 로 바꾼 이름. 같은 날 두 차례 상속이 비어 실제로 필요했다
- **턴 중간 메시지 (2026-10-28):** 작업 중 사용자가 보낸 메시지는 `type == "user"` 행이 아니라 `type == "attachment"` 행의 `rendered[].content`(같은 내용이 `api-request-blob` 의 `message.content[].text` 에도)에 `The user sent a new message while you were working:` 뒤에 실린다 — transcript 를 스캔할 때 이 마커를 grep 해 함께 수집한다. 한 세션의 피드백 4건 중 3건이 이 경로였다
- **결과 보고 전체를 마지막 메시지 하나에 담는다.** 표를 여러 턴에 나눠 출력하면 앞부분이 유실된다
- 중간 진행 상황을 사용자에게 알리려 하지 않는다 — 어차피 전달되지 않는다
- 사용자에게 확인이 필요한 사항(병합·분할 제안)은 마지막 메시지 안에 **질문 형태로 남긴다**. fork 안에서 사용자에게 직접 물을 수 없다

## 규칙

- **규칙을 없애지 않는다.** 병합은 중복 서술만 제거하는 것 — 규칙 자체를 없애는 것이 아니다. 압축·아카이브 이동은 삭제가 아니다 (원문이 `style-archive/` 에 보존되므로)
- **병합·압축은 사용자 승인 후 적용한다.** 보고에 제안만 남기고 임의로 재구성하지 않는다
- 주제 파일을 새로 만들거나 나누지 않는다 (사용자 승인 시에만 예외)
- 칭찬은 **왜 칭찬했는지 분석**하여 해당 주제 파일의 "잘한 것 / 유지할 것" 섹션(없으면 만든다)에 규칙 형태로 기록한다 — 세션 성과 일지("X 버그를 발견함")가 아니라 재적용 가능한 행동 규칙("~할 때 ~한다")으로. 항목 작성 규격의 칭찬 조항 준수
