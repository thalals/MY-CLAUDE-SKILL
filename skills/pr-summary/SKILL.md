# PR 이슈·원인·작업 내용·영향 정리

수정한 변경을 PR 본문이나 공유용으로 **이슈 → 원인 → 작업 내용 → 영향** 네 주제의 짧은 마크다운으로 정리한다.

## 사용법

```
/pr-summary
```

대화에서 원인 분석과 수정이 끝난 뒤 "PR 에 공유하게 정리해줘" 같은 요청이 오면 호출한다.

## 실행 절차

### 1단계: 사실 모으기
- 변경분은 실제 diff 로 확인한다 — 작업 트리면 `git diff -- <바꾼 파일>`, 브랜치면 `git diff <base>...HEAD`. 대화 기억으로 쓰지 않는다
- 이슈·원인은 대화에서 확인한 진단을 쓴다. 실측(조회 결과, 데이터)과 코드 읽기로 추론한 것을 구분해 둔다
- 영향은 바뀐 코드의 호출처·필터·조건 조합을 다시 따라가 "달라지는 것" 과 "그대로인 것" 을 가른다

### 2단계: 템플릿으로 작성
- 아래 템플릿 그대로, 각 주제는 불릿 1~4줄
- 주제 이름과 순서는 바꾸지 않는다. 해당 내용이 없는 주제만 뺀다
- 결과는 붙여넣기 쉽게 하나의 ```` ```markdown ```` 코드 블록으로 낸다

```markdown
#### 이슈
<사용자 관점의 증상 한 줄>
- 예: <재현되는 구체 데이터 하나와 조건>

#### 원인
<어디서(파일·메서드) 무엇이 잘못됐는지 한 줄>
- <그 결과가 왜 증상으로 이어지는지 메커니즘>

#### 작업 내용
- <변경 1: 무엇을 → 어떻게>
- <변경 2>
- <삭제한 잔재가 있으면 그것도>

#### 영향
- <바뀌는 동작>
- <바뀌지 않는 동작 — 리뷰어가 걱정할 만한 것 위주>
- <성능·호환·데이터 측면 (근거가 있을 때만)>
```

### 3단계: 작성 규칙
- **이슈**: 증상은 사용자가 본 그대로(화면·API·데이터). 내부 용어로 바꾸지 않는다
- **원인**: 코드 위치 + 메커니즘. "~때문으로 보임" 같은 추론이면 그렇게 적고, 실측으로 확인했으면 단정한다
- **작업 내용**: diff 에 있는 것만. 변경 하나당 불릿 하나, `A → B` 형태로 이동·교체를 드러낸다
- **영향**: 바뀌는 것과 바뀌지 않는 것을 둘 다 쓴다. 근거 없는 성능 주장, 하지 않은 테스트·검증은 쓰지 않는다
- 코드 식별자·컬럼·파일명은 백틱, 문장은 짧은 서술형. 이모지·장식 헤더를 더하지 않는다
- 전체 분량은 한 화면 안. 길어지면 영향의 세부를 줄이고 원인·작업 내용은 남긴다

### 4단계: 전달
- 코드 블록만 내고, 블록 밖에는 필요한 경우에만 한 줄(확인하지 못한 항목 등)을 덧붙인다
- PR 생성·코멘트 작성·외부 전송은 사용자가 요청할 때만 한다
